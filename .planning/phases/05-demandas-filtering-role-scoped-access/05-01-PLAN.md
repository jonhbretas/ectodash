<objective>
**Phase goal (per ROADMAP.md):** Users can filter/group demandas and only see/edit what their role permits, through short, accessible forms.

This plan is Wave 1 — the phase's schema-and-RLS tracer, proven live against the real hosted project before any filtering UI is built on top of it (Wave 2, plan 05-02). It does three things in one migration: (1) closes the área-to-líder data-model gap with a `lider_areas` many-to-many join table — per the user's locked decision that a líder can lead multiple áreas simultaneously, superseding 05-RESEARCH.md's own `[ASSUMED]` single-column recommendation; (2) narrows `demandas`' and `demanda_responsaveis`' permissive Phase-4 RLS to the role/ownership-scoped rules DEM-05 requires, with the SELECT and UPDATE predicates on `demandas` built textually identical so the Phase 2 SELECT-gates-UPDATE trap cannot silently reappear; (3) re-verifies `demandas_com_status`'s `security_invoker=true` view still reflects the narrowed policy, and updates the one Phase-4-era test whose premise (any authenticated user can edit any demanda) this migration deliberately breaks.

This is deliberately its own early, carefully-tested wave, separate from plan 05-02's filtering UI — narrowing SELECT on a live table with existing production data (Phase 4 demandas) is the highest-risk change in this phase, and every role-scoping assertion must be proven via a service-role re-read before any UI is built to assume it works.

Purpose: get the one hardest-to-reverse, highest-risk decision right and proven live — narrowing visibility/editability on a production table without silently breaking write access for a role that should still have it — before any UI depends on the result.
Output: `supabase/migrations/0004_demandas_role_scope.sql` applied to the live hosted project, `tests/db/demandas-rls.test.ts` extended with the full role-scoping re-verification matrix (including a rewritten Phase-4-era test), and `docs/areas.md` documenting the coordenador-only área-assignment procedure.
</objective>

The composite primary key is the many-to-many mechanism per the locked decision: a líder can hold multiple rows (multiple áreas), and the same área string can appear under multiple líderes if the institution ever has co-leadership (not excluded by this design, though not required by DEM-05 either).
