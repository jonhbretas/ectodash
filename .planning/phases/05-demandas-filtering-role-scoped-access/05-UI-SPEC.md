# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Sequencing Note (read first)

This phase adds a **new UI surface** (filter/group controls) on top of already-shipped,
already-shadcn-retrofitted screens (`demanda-list.tsx`, `demanda-card.tsx`, `demanda-table.tsx`,
`status-badge.tsx`, `overdue-badge.tsx` — all Phase 3-retrofitted onto shadcn `Button`/`Input`/
`Label`/`Select`/`Badge`/`Table` primitives). This contract **extends** the locked token language
from `03-UI-SPEC.md`/`04-UI-SPEC.md` — no new hue, spacing value, or type size is introduced.
`shadcn init` already ran in Phase 3 (`components.json` present, style `radix-vega`, base color
`neutral`, icon library `lucide`) — no shadcn gate needed this phase.

**Data-model gap found during research (flagged, not silently assumed):** `área/projeto` is a
single free-text column (`public.demandas.area`, confirmed in `supabase/migrations/0003_demandas.sql`)
— there is no separate "projeto" column. The roadmap's "filter by área, projeto, or responsável"
(DEM-04) is satisfied by **one** área/projeto filter dimension plus one responsável filter
dimension, not three independent ones. This spec treats área and projeto as the same field
throughout, matching the data model — do not build two separate filter inputs for one column.

**Second data-model gap found during research:** `public.profiles` has no `area` column — a líder
de área's "área" is not stored anywhere in the database today (confirmed via
`supabase/migrations/0002_profiles_role.sql`). DEM-05's "líder de área vê as da sua área" cannot be
implemented without adding this. **This is a schema/RLS decision, not a UI decision** — this
UI-SPEC assumes the planner/RESEARCH.md adds a `profiles.area text` column (mirroring `demandas.area`'s
free-text shape, so a líder's assigned área can be string-matched against a demanda's área) and
specs the UI on that assumption. If the planner chooses a different mechanism (e.g. an
área-lider link table), the visual contract below (a scoped-view notice, no separate área-management
screen) still holds — only the underlying query changes.

## Filter State Pattern (informs layout, not just behavior)

**Decision: URL search params (`?area=...&responsavel=...&agrupar=...`), read directly by the
Server Component, not client-side state.**

Rationale, consistent with this project's established pattern (`(dashboard)/page.tsx` is already a
Server Component fetching directly from Supabase, per Phase 4's shipped code):
- Filters become shareable/bookmarkable links (a coordenador could send a líder a pre-filtered URL)
- No client-side state library or `useState`/`useEffect` fetch-on-change dance is needed — the
  Server Component re-runs its Supabase query with the new search params on navigation, matching
  the zero-JS-fetch-waterfall principle Phase 4's research already established for the list itself
- Browser back/forward naturally undoes/redoes filter changes — valuable for the elderly-inclusive
  audience, who benefit from relying on familiar browser navigation rather than an in-app "undo"
- The filter `<Select>` controls are Client Components (they need `onValueChange`), but they only
  ever call `router.push`/`replace` with updated search params — they do not hold the filtered
  *data* in client state, only the *control* state momentarily during interaction

**No RESEARCH.md exists yet for this phase at the time of this UI-SPEC** (checked — directory was
empty before this file was created); this pattern is this document's own recommendation, grounded
in the identical precedent already shipped in Phase 4 (`demanda-table.tsx`'s `useRouter().push`
for row-click navigation is the same "Client Component triggers navigation, Server Component owns
data" split). If `05-RESEARCH.md` lands with a conflicting recommendation, the planner reconciles
against this document rather than silently preferring one, per this project's own established
Phase 3 precedent for handling out-of-order artifacts.

## Screen Inventory

### 1. Filter bar (new — sits directly below the existing page header, above the list, on the
same route: `/`)

**Purpose:** lets the user narrow the already-role-scoped list by área/projeto and/or responsável,
and optionally group it. Must work identically whether 0, 1, or many demandas exist post-filter.

**Layout — mobile (< 640px):**
- Filter controls stack full-width, vertically, `gap-4` (16px), directly below the header row
  (heading + count + "Nova demanda" button) and above the list/empty-state
- Order top to bottom: Área/projeto `Select` → Responsável `Select` → Agrupar por `Select`
- Each `Select` is full-width, `min-h-14`, label above using the shared `Label` component
  (`text-xl font-medium text-zinc-900`), matching the exact field-label treatment from
  `demanda-form.tsx`
- Active-filter chips (if any) render as a wrapping row directly below the three `Select`s,
  `gap-2` (8px) between chips, each chip is `bg-zinc-100 text-zinc-700 rounded-full px-2 py-0.5
  text-base` with an inline `×` remove control (lucide `X`, 14px, `aria-label` per the Copywriting
  Contract)
- `Limpar filtros` button (only rendered when ≥1 filter is active) appears full-width below the
  chips, outline/secondary style (`border border-zinc-400 bg-white text-zinc-900`, `min-h-14`,
  matching the existing `Cancelar` button style from `demanda-form.tsx`) — NOT the primary blue,
  since clearing is a reset action, not the primary task

**Layout — desktop (≥ 1024px, same `lg` breakpoint the list already uses):**
- Filter controls render in a single horizontal row, `gap-4` (16px) between each `Select`, each
  `Select` sized `w-56` (fixed width, not full-width, since 3 side-by-side full-width selects would
  be visually noisy on a wide screen) — Área/projeto, Responsável, Agrupar por, left to right
- Active-filter chips render inline to the right of the three selects on the same row if they fit
  (`flex flex-wrap`), wrapping to a second line if the viewport is narrower than needed — never
  causes horizontal scroll
- `Limpar filtros` renders as a plain-text/ghost-style button (not full button chrome) at the
  right edge of the filter row when active, to avoid competing visually with "Nova demanda" in the
  header above

**Interaction with the existing card/table breakpoint switch:** the filter bar itself does NOT
follow the card/table `lg:` switch — it is the same three-`Select` control set at every breakpoint,
only its internal layout (stacked vs. inline row) changes at `lg`. It sits structurally between
the existing header block and the existing `<ul>`/`<table>` conditional render in
`demanda-list.tsx`, unchanged by this phase.

**Interaction with existing sort order:** filtering never changes the sort rule already locked in
`04-UI-SPEC.md`/implemented in `demanda-list.tsx`'s `compareDemandas` — atrasada-first, then prazo
ascending, then concluída-last is applied to whatever subset of demandas the filter/role-scope
produced, in every case (filtered, grouped, or both).

### 1a. Grouped view (when "Agrupar por" is set to área or responsável)

**Layout:** the list is split into labeled sections, one per distinct group value, each section
using:
- A group heading, `text-2xl font-semibold text-zinc-900` (same weight/size as the page `h1`, one
  level visually subordinate via being preceded by the page header, not by a smaller font size —
  keeps headings legible for the elderly-inclusive audience rather than shrinking sub-headings)
- Immediately followed by that group's count, `text-base text-zinc-700`, same "{N} demanda(s)"
  pattern as the page-level count
- Then the same card list (mobile) or table (desktop) rendering as the ungrouped view, scoped to
  that group's rows only — sort order (atrasada-first, prazo-ascending, concluída-last) applies
  **within each group independently**, not globally across groups
- `gap-8` (2×`lg`, i.e. 32px — reuses the existing `xl` token, no new spacing value) between group
  sections for clear visual separation
- A demanda with no área set (when grouping by área) falls into a final group headed
  `Sem área definida` — reuses the exact placeholder string already used for the empty-área chip
  on individual cards (`demanda-card.tsx`/`demanda-table.tsx`), never silently dropped from the
  grouped view

**Grouping and filtering combine:** if both a filter (e.g. área = "Pesquisa de Campo") and
group-by (e.g. responsável) are active, the grouped view renders only within the already-filtered
subset — group-by never re-introduces rows the filter excluded.

### 2. Filtered-to-zero-results empty state (distinct from Screen 2 in `04-UI-SPEC.md`, "no
demandas at all")

Renders in the exact same layout slot as the existing empty state (centered block, `py-16`), but
with different copy and a different icon to avoid the user mistaking "your filter matched nothing"
for "there is no data in the system at all" — a meaningfully different situation requiring a
different next action (adjust the filter vs. create a demanda):

- Icon: lucide `FilterX`, 48px, `text-zinc-400` (distinct from the "no demandas at all" state's
  `ClipboardList` icon — different icon reinforces this is a filter-caused empty state, not a
  data-absence one)
- Heading (30px semibold): `Nenhuma demanda encontrada com esses filtros`
- Body (20px, `text-zinc-700`, `max-w-md`): `Tente escolher outra área, projeto ou responsável, ou
  toque em "Limpar filtros" para ver todas as demandas.`
- CTA button: `Limpar filtros`, outline/secondary style (`border-zinc-400 bg-white text-zinc-900`,
  `min-h-14`) — deliberately NOT the primary blue `Nova demanda`-style button, since this state's
  correct next action is "undo your filter," not "create something new." The existing "Nova
  demanda" CTA in the page header above remains visible and functional throughout, so creating a
  demanda is still one tap away without needing a second CTA in the empty-state body.

**Distinction from the "no demandas at all" state is structural, not just copy:** the "no demandas
at all" state (from `04-UI-SPEC.md`) only ever renders when the **unfiltered, role-scoped** dataset
is empty (e.g. a brand-new voluntário with zero assigned demandas). The filtered-to-zero state
renders whenever a filter is active AND the filtered result set is empty, even if the unfiltered
role-scoped dataset is non-empty. These are mutually exclusive conditions — never render both, and
never render the filtered-to-zero copy when the reason for zero results is actually "no demandas
exist for this user at all" (in that case, render the original Screen 2 empty state even if a
filter happens to be technically active, since "create your first demanda" is still the more
useful message).

### 3. Role-scoped-view notice (new — small text element, not a screen)

**Purpose:** gives a líder de área or voluntário comum a lightweight, always-visible signal that
they are looking at a subset, without implying something is broken or hidden from them
maliciously.

**Layout:** a single line of `text-base text-zinc-700` copy, placed directly below the page header
(`Demandas` / count) and above the filter bar, `gap-2` (8px) below the header row. No icon, no
box/border, no background chip — this is calm informational text, not a warning (there is nothing
wrong with seeing a scoped view; it is the expected, correct behavior for these roles).

- **Voluntário comum:** `Mostrando apenas as demandas atribuídas a você.`
- **Líder de área:** `Mostrando as demandas da área {área do líder}.` — the área name is
  interpolated from the líder's own `profiles.area` value (see the data-model gap noted in the
  Sequencing Note above)
- **Coordenador geral:** no notice rendered at all. Per the "don't add UI for the unrestricted
  case" principle — a coordenador already sees the literal total count of every demanda in the
  system via the existing count badge, which is itself sufficient confirmation of an unscoped view.
  Adding a notice like "Mostrando todas as demandas" would be redundant chrome for the one role
  that has no restriction to explain.
- **Financeiro:** not addressed by this phase's success criteria (DEM-05 names only voluntário
  comum, líder de área, coordenador) — if a `financeiro` account can reach this list at all
  (undetermined by this phase's scope), it inherits whichever RLS scoping the planner assigns it;
  this UI-SPEC does not speculate a notice string for a role the roadmap doesn't mention here.

This notice is server-rendered from the same Server Component that already knows the current
user's role/profile (extending the existing `supabase.auth.getUser()` + `profiles` read already
present in `page.tsx`) — no additional client-side role check, consistent with CLAUDE.md's "What
NOT to Use" entry against client-side-only authorization/role logic. This is a UX convenience
label, not a security boundary — RLS remains the only real authorization enforcement, as it
already is for every other scoped read in this project.

## Responsável Picker — Role-Scoping Question (demanda-form.tsx)

**Decision: do NOT scope the responsável picker to a líder's área this phase — keep it showing
every profile, as it already does.**

Reasoning:
- The roadmap's DEM-05 success criterion is about **visibility** of demandas ("vê e edita só
  suas... vê as da sua área... vê tudo") — it does not state a constraint on **who a líder may
  assign as responsável**. Narrowing the assignment picker is a plausible future hardening, not a
  requirement this phase's success criteria actually name.
- Institutionally, a líder de área may legitimately need to assign a cross-área collaborator (e.g.
  borrowing a volunteer from another área for one task) — silently restricting the picker to
  same-área profiles would block a real workflow without any stated justification for that
  restriction.
- Scoping the picker would require the same `profiles.area` data-model addition flagged in the
  Sequencing Note, compounding an already-flagged schema gap with a second inferred requirement
  not stated in DEM-04/DEM-05/UX-02's actual text.

**If the planner's RESEARCH.md or the user's CONTEXT.md later decides otherwise:** the visual
change would be additive (filtering the existing `<select multiple>` / eventual shadcn `Select`
option list by the acting líder's área) and would not require any different component — flagging
this here so it isn't silently invented as a requirement by the executor, and isn't silently
dropped if a future decision does want it.

**No new admin/assignment screen is introduced this phase.** Per the roadmap and Phase 2's
established pattern, role and área assignment remain a CLI/SQL/runbook operation (mirroring
`docs/roles.md`'s existing `--role` flag pattern for role assignment) — there is no phase in the
roadmap that creates an admin UI for managing áreas or líderes, and this phase's own success
criteria (filtering, scoped visibility, short forms) do not require one. If área assignment needs
a UI later, it is a new phase's concern, not an unstated scope addition here.

## UX-02 Applied — Short Forms, Few Fields, Clear Confirmation

This phase introduces **no new multi-field form** — the filter bar is UX-02-adjacent (it is a
lightweight "form" of 2-3 optional `Select` inputs) but is not a create/edit form, and no new
admin/assignment screen is built (see above). UX-02's requirement is therefore satisfied this
phase primarily by:

1. **The filter bar itself stays at 3 controls max** (área/projeto, responsável, agrupar por) —
   never grows into a "filter form" with more fields; this cap is a deliberate UX-02-style
   constraint applied to a non-mutating control surface, not just to mutating forms.
2. **No filter action requires a "confirm" step** — every filter change (`Select` value change,
   chip removal, "Limpar filtros") applies immediately and reversibly (browser back undoes it),
   because filtering is non-destructive and has no "important action" weight — UX-02's
   confirmation clause applies to consequential mutations, not to read-only view adjustments. This
   is a deliberate, stated reading of UX-02 for this phase: **confirmation is reserved for actions
   that change data**, not actions that change what's currently visible.
3. **Existing forms are unchanged.** `demanda-form.tsx` (create/edit, 5 fields) and the one-tap
   `Marcar como concluída` action already satisfy UX-02's "short, few fields, clear confirmation"
   bar per `04-UI-SPEC.md`'s own contract — this phase does not need to re-litigate or expand that
   form. If a future need arises for a genuinely new confirmable action in this phase's scope
   (there is none identified in DEM-04/DEM-05), it would follow the same pattern already
   established: a distinctly-spaced (`gap-6`), differently-colored action button separate from the
   primary form flow, exactly as `Marcar como concluída` already demonstrates.

## Open Decisions (flagged for later review, not blocking)

1. **`profiles.area` column does not exist yet.** DEM-05's líder-de-área scoping cannot be
   implemented without it (or an equivalent área-to-líder mapping). This UI-SPEC assumes a
   free-text `profiles.area` column matching `demandas.area`'s shape, string-matched for RLS/query
   purposes — the planner/RESEARCH.md owns the final schema decision; the UI contract (scoped-view
   notice text, área filter behavior) holds regardless of the underlying mechanism chosen, as long
   as each líder resolves to exactly one área string.
2. **Área/projeto free-text fragmentation risk (carried forward from `04-UI-SPEC.md` Open Decision
   #2, now directly relevant).** The área filter's `Select` options come from `DISTINCT area` over
   visible rows — if the same área was typed inconsistently (`"Pesquisa de Campo"` vs `"pesquisa
   de campo"`), the filter dropdown will show both as separate options, silently fragmenting what
   the coordenador considers one área. This UI-SPEC does not solve normalization (that's a
   data-model decision, not a visual one) but flags that the filter dropdown will faithfully
   surface any existing fragmentation rather than hide it — worth a coordenador-facing data-quality
   check post-launch, not a blocker for this phase.
3. **Responsável picker área-scoping for líderes** (see dedicated section above) — explicitly
   deferred, not built this phase, with the reasoning recorded so it isn't silently reintroduced or
   silently forgotten.
4. **Loading-state perceptibility during filter-driven navigation** — flagged as a 🧪 backstop in
   UI Considerations; needs a verify-time check on real network latency, same treatment Phase 4
   gave its own initial-list-load skeleton question.
