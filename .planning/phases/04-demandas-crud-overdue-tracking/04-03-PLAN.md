    **1. Extend `demanda-form.tsx`** to support an edit mode. Add optional props: `demandaId?: number`, `defaultValues?: Partial<DemandaFormValues>` (título, current responsavelIds array, prazo, status, área pre-filled from the loaded demanda), and `mode: "create" | "edit"`. When `mode === "edit"`: submit button copy is `Salvar alterações` (`Salvando...` while pending, per 04-UI-SPEC.md), and the form's `action` binds to `updateDemanda` (below) via `.bind(null, demandaId)` — matching the `bind(id)` pattern RESEARCH.md's Pattern 5/Code Examples describes for passing a server-trusted id alongside `useActionState`'s `(prevState, formData)` signature. Keep the `Cancelar` button behavior identical to create mode (returns to `/` without saving). Do not fork a second component — one `DemandaForm` handles both modes via these props.

    **2. `updateDemanda(id, prevState, formData)`** in `actions.ts`, `"use server"`:
    - `supabase.auth.getUser()` — no user, return the same session-expired message as `createDemanda`.
    - Parse `formData` the same way `createDemanda` does (`getAll("responsavelIds")` for the array field, not `Object.fromEntries`).
    - `id` comes from the function's own parameter (bound server-side via the form's `action`), never read from `formData` — this is the same discipline plan 04-02 already applied to `criado_por`, now applied to the row being targeted (RESEARCH.md Pitfall 4's general principle, RESEARCH.md Code Examples' own comment: "id comes from a server-trusted route param/bind(), never from formData itself").
    - `.from("demandas").update({ titulo, prazo, status, area }).eq("id", id)` — do not include `criado_por` in the update payload; it is set once at creation and never changed.
    - **Responsável diffing**, after the demandas update succeeds: read the demanda's *current* `demanda_responsaveis` rows for this `id` (a fresh query, not trusted from client state — the client's idea of "current" could be stale). Compute the set difference against `parsed.data.responsavelIds`: ids to add (in the new set, not in current) get inserted; ids to remove (in current, not in the new set) get deleted. Issue one batched `.insert([...])` for additions (if any) and one `.delete().in("profile_id", [...]).eq("demanda_id", id)` for removals (if any) — skip either call entirely when its list is empty, don't issue a no-op insert/delete. This is the delete-then-insert pattern plan 04-01's RLS was built for, now driven by an actual diff instead of a blind full-replace.
    - On any failure, log via `console.error` and return `{ ok: false, message: "Não foi possível salvar as alterações." }` (04-UI-SPEC.md's edit-specific copy, distinct from create's message).
    - `revalidatePath("/")`. Return `{ ok: true, message: "Demanda atualizada." }`.

    **3. `concludeDemanda(id)`** in `actions.ts`, `"use server"` — a narrower, separate action (not a call into `updateDemanda`, per RESEARCH.md's own rationale: "a smaller, more auditable mutation surface for a single-field status change"):

    - `.from("demandas").update({ status: "concluida" }).eq("id", id)`.
    - On failure, log and return `{ ok: false, message: "Não foi possível concluir a demanda." }`.
    - `revalidatePath("/")`. Return `{ ok: true, message: "Demanda concluída." }`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Route param `id` -> updateDemanda/concludeDemanda | The client legitimately names which demanda to edit; RLS (plan 04-01) is what actually authorizes the write, not this plan's application code |
| Client-submitted `responsavelIds` -> demanda_responsaveis diff | A client claiming a stale "current" responsável set could produce an incorrect diff if the server trusted client-reported "current" state instead of re-querying |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-11 | Tampering | A client submitting an `id` for a demanda it should not be able to edit | low | accept | This phase's RLS (plan 04-01) permits any authenticated user to UPDATE any demanda by design (CONTEXT.md RLS Scope) — this is not a bug to mitigate in this plan, it is the deliberately broad v1 policy Phase 5 narrows |
| T-04-12 | Tampering | Responsável diff computed against a client-supplied "current" set instead of the database's actual current set, producing an incorrect add/remove result | medium | mitigate | `updateDemanda` re-queries `demanda_responsaveis` for the real current set server-side before diffing — the client's form state is only the *desired* end state, never trusted as the starting point |
| T-04-13 | Repudiation | No audit trail of who changed which fields on a demanda, or who removed a responsável | low | accept | Same disposition as plan 04-01's T-04-05 — acceptable for v1 at this institution's scale; `updated_at` gives a partial signal |
| T-04-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs zero new packages — pure extension of plan 04-02's already-audited dependencies |
</threat_model>
