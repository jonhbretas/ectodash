# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Sequencing Note (read first)

Phase 3 ("Accessible UI Foundation") was deferred by the user to run **after** this phase, so
this UI-SPEC is not consuming an existing design system — it is establishing the first real one.
Every token below is deliberately small, explicit, and copy-pasteable so Phase 3 can lift it
wholesale into shared primitives/CSS variables rather than reconcile two systems. This phase
extends, and does not contradict, the accessibility floor already shipped in
`src/app/(auth)/login/login-form.tsx` and `sign-out-button.tsx` (Phase 1): `text-xl` body,
`min-h-14` controls, `px-4 py-3` padding, AA-contrast zinc/blue palette, visible focus rings,
pt-BR copy.

**shadcn/ui decision:** CLAUDE.md recommends shadcn/ui, but `components.json` does not exist yet
and `skip_discuss` is active for this phase (no interactive init gate). Rather than block on an
interactive `npx shadcn init` prompt, this phase builds plain Tailwind v4 components matching the
Phase 1 accessibility floor (native `<input>`, `<select>`, `<button>`, `<form>` — no headless
library dependency yet). This keeps Phase 4 unblocked and keeps every visual token in this
document trivially portable into shadcn's CSS-variable theme format when Phase 3 runs `shadcn
init` and formalizes the system. Logged as an open decision below for visibility, not as a block.

## Typography

3 sizes, 2 weights — deliberately smaller set than Phase 1's ad hoc usage so Phase 3 can lift this

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body / input / label | 20px (`text-xl`) | 400 regular | 1.5 |

## Color

Reuses Phase 1's exact zinc/blue/red palette — no new hues introduced except one addition
(amber) required for the 3-state status system (see below). All pairs listed meet WCAG AA
(4.5:1) for normal text; contrast ratios computed against the stated background.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `zinc-50` (#FAFAFA) bg / `zinc-900` (#171717) text | Page background, primary body text — contrast 19.6:1 |
| Secondary (30%) | `white` (#FFFFFF) surface, `zinc-400` (#A1A1AA) border | Demanda cards, form containers, input borders |
| Accent (10%) | `blue-700` (#1D4ED8) | **Reserved for:** primary CTA buttons ("Criar demanda", "Salvar"), active/focused input outline, links, the "em andamento" status badge |
| Destructive | `red-700` (#B91C1C) | **Reserved for:** atrasada (overdue) flag, delete-confirmation button, field validation error text/border. Text-on-white contrast 5.9:1 |
| Success/neutral-positive | `green-700` (#15803D) | **Reserved for:** "concluída" status badge only. Contrast on white 5.1:1 |
| Warning | `amber-700` (#B45309) | **Reserved for:** "pendente" status badge only (paired with an icon, never alone — see Status Representation). Contrast on white 4.6:1 |

Accent reserved for: primary submit/create buttons, active focus ring, text links, "em
andamento" status badge fill. Never used for body text, borders, or decorative elements —
matches Phase 1's existing usage where `blue-700` is exclusively the submit button and focus
ring.

**Explicit non-color-alone rule (ties to success criterion 3 and Status Representation below):**
every status and the overdue flag pairs color with both an icon (lucide-react) and a text label.
No status or flag in this phase is conveyed by color/background alone.

## Screen Inventory

### 1. Demandas list (`/` — the dashboard route, replaces the current placeholder text)

**Purpose:** primary view; the first thing every user sees after login. Must read correctly for
0, 1, and many demandas.

**Layout — header (all breakpoints):**
- `h1`: `Demandas` — 24px semibold (`text-2xl font-semibold text-zinc-900`)
- Count badge next to heading, small/16px zinc-700, e.g. `12 demandas` (or `1 demanda` — this is
  the one spot with singular/plural copy variance, since it sits directly beside the count)
- Primary CTA button, top-right on desktop / full-width below header on mobile: `Nova demanda`
  (`min-h-14`, `bg-blue-700`, `text-xl`, matches `SubmitButton` styling from login-form.tsx)

**Layout — mobile (< 640px, `sm` breakpoint), card list, NOT a table:**
Each demanda renders as a card, full-width, stacked vertically with `gap-4` (16px) between cards,
`p-4` (16px) internal padding, `bg-white`, `border border-zinc-300`, `rounded-lg`:
- Row 1: título (18px/`text-lg` semibold, `line-clamp-2`) + status badge top-right of card
- Row 2: responsável name, 16px zinc-700, prefixed with a person icon (lucide `User`, 16px)
- Row 3: prazo date (dd/mm/aaaa via date-fns), 16px, prefixed with a calendar icon (lucide
  `Calendar`, 16px) — if overdue, this entire row swaps to the Atrasada treatment (see below)
- Row 4 (only if área/projeto set): área/projeto as a small neutral chip, `bg-zinc-100
  text-zinc-700`, else the `Sem área definida` placeholder chip in `bg-zinc-100 text-zinc-500`
- Entire card is a tap target (wraps in a `<Link>` to the edit form) — min height naturally
  exceeds 56px given the 4 stacked rows + padding, no separate "Editar" button needed on mobile

**Layout — desktop (≥ 1024px, `lg` breakpoint), table:**
Standard `<table>` with columns: Título | Responsável | Prazo | Status | Área/Projeto | (row
click → edit, whole `<tr>` has `cursor-pointer` + hover `bg-zinc-50`). Header row `bg-zinc-100
text-zinc-700 text-base font-semibold`. Body rows `text-xl` per the body type scale, `min-h-14`
per row (`py-3` cell padding). Overdue rows get a `border-l-4 border-red-700` left-edge stripe in
addition to the inline Atrasada badge in the Prazo cell — a redundant-but-scannable second signal
for a table full of rows.

**Layout — tablet (640–1023px):** use the mobile card list (cards read fine at this width; a
cramped table does not). Single breakpoint switch at `lg` keeps this simple for Phase 3 to
extend later.

**Sort order:** atrasada items first, then by prazo ascending (soonest deadline next), then
concluída items last regardless of prazo — surfaces what needs attention without requiring the
user to sort manually (directly serves the phase goal).

### 2. Empty state (no demandas yet)

Renders in place of the list (same header above it, so the "Nova demanda" CTA is still visible
top-right/top-of-page). Centered block, `py-16` (64px) vertical padding:
- Icon: lucide `ClipboardList`, 48px, `text-zinc-400`
- Heading (30px semibold): `Nenhuma demanda cadastrada ainda`
- Body (20px, `text-zinc-700`, max-width `max-w-md` for readable line length):
  `Quando alguém criar uma demanda, ela vai aparecer aqui. Toque em "Nova demanda" para começar.`
- Inline CTA button (same style/copy as header CTA): `Nova demanda`

### 3. Create form (`/demandas/nova`)

**Layout:** single column, `max-w-md` (matches login form width), one field visually per row,
`gap-4` (16px) between fields — never more than 5 fields on one screen (título, responsável,
prazo, status, área/projeto), satisfying the "short forms" spirit even though Phase 5 owns the
formal UX-02 requirement.

Field order (top to bottom): Título → Responsável → Prazo → Status → Área/projeto.

- **Título*** — `<input type="text">`, label above field (`text-xl font-medium`), `min-h-14`,
  `px-4 py-3`, placeholder is NOT used for the label (label is always visible above, per the
  brief) — placeholder attribute holds a short example only: `Ex: Revisar relatório mensal`
- **Responsável*** — `<select>` populated from institution profiles (full name), same input
  styling as título, `min-h-14`. Native select chosen over a custom combobox — see Date/Select
  Input Approach below for rationale (applies to both).
- **Prazo*** — native `<input type="date">` — see dedicated section below.
- **Status** — `<select>` with 3 options (Pendente / Em andamento / Concluída), defaults to
  `Pendente` on create (no empty/placeholder option — a demanda always has a valid status).
  Marked without `*` since it always has a valid default; still visually identical field
  treatment.
- **Área/projeto** — `<input type="text">`, explicitly the only optional field, label reads `Área
  ou projeto` with no asterisk, placeholder example: `Ex: Pesquisa de Campo`
- Legend line directly under the `h1`/form title: `Campos com * são obrigatórios.` (16px,
  zinc-600)
- Submit button: `Criar demanda`, full width, same `SubmitButton` component pattern as Phase 1
  (disabled + `Criando...` label while `useFormStatus` pending)
- Cancel: plain-style button below submit, `Cancelar`, `border border-zinc-400 bg-white`
  (secondary style matching `SignOutButton`), returns to the list without saving

### 4. Edit form (`/demandas/[id]/editar`)

Identical field layout/order/styling to the create form, pre-filled with the demanda's current
values. Two differences:
- Submit button copy: `Salvar alterações` (`Salvando...` while pending)
- A secondary, clearly-separated action below the form (not inline with Cancelar/Salvar, given
  extra `gap-6`/24px spacing to signal it's a distinct action, not a third form button in the
  same row): `Marcar como concluída` — a single-tap button (`bg-green-700` text-white, `min-h-14`)
  that sets status to Concluída and saves immediately, without re-opening the status dropdown.
  This directly serves success criterion 2 ("edit ... and mark it as concluded") as a one-tap
  shortcut rather than requiring the user to open the Status select and pick the third option
  manually — critical for the elderly-user low-friction goal. The Status dropdown in the form
  above remains available for the reverse case (reopening a concluded item) or picking "Em
  andamento" directly.

## Overdue ("Atrasada") Visual Treatment

**Definition:** `prazo < today` AND `status != 'concluída'`. A concluded demanda is never shown
as atrasada regardless of its prazo — finishing late is not the same as being currently overdue.
This is a computed/derived visual state, never a stored column — matches success criterion 3's
"automatically."

**Non-color-alone treatment (both breakpoints):**
1. **Icon:** lucide `AlertTriangle`, 16-20px, `text-red-700`, placed immediately before the
   prazo date text
2. **Color:** prazo date text and icon in `red-700` (instead of the default `zinc-900`/`zinc-700`)
3. **Text label:** the word `Atrasada` rendered as a small pill/badge (`bg-red-100 text-red-800
   border border-red-300`, `text-base font-semibold`, `rounded-full px-2 py-0.5`) — never
   conveyed by the red color alone, the word itself is always present
4. **Table-only extra signal:** `border-l-4 border-red-700` left stripe on the row (desktop table)
5. **Accessible name:** the badge carries `aria-label="Atrasada — prazo era {dd/mm/aaaa}"` so a
   screen reader announces the reason, not just the word

This 3-layer redundancy (icon + color + text, with a 4th on desktop) satisfies "must NOT rely on
color alone" for both colorblind users and low-vision elderly users who may not perceive the red
hue clearly at small sizes.

## Status Representation

Three states — pendente / em andamento / concluída — each rendered as a badge pairing an icon,
color, and always-visible text label (never color-alone, same principle as Atrasada):

| Status | Icon (lucide-react) | Color | Badge style |
|--------|---------------------|-------|-------------|
| Pendente | `Circle` (outline) | `amber-700` on `amber-100` | `border border-amber-300` |
| Em andamento | `Clock` | `blue-700` on `blue-100` | `border border-blue-300` |
| Concluída | `CheckCircle2` (filled) | `green-700` on `green-100` | `border border-green-300` |

Badge shape/sizing is identical across all 3 states and identical to the Atrasada badge
(`rounded-full px-2 py-0.5 text-base font-semibold`) — only the icon/color/text vary, keeping
the pattern predictable. The Atrasada badge, when applicable, renders **in addition to** the
Status badge (a demanda can be simultaneously "Pendente" and "Atrasada") — they are not mutually
exclusive, placed side by side with `gap-2` (8px).

## Date Input Approach (Prazo field)

**Decision: native `<input type="date">`, no custom date-picker library.**

Rationale, judged specifically for an elderly user on a phone (per the brief):
- Native date inputs on iOS/Android render the OS's own well-tested date wheel/calendar
  picker — already familiar to any user who has set an alarm or booked anything on their phone,
  requiring zero new UI literacy
- Avoids shipping and QA-ing a third-party JS date-picker library's touch-target sizing, which
  frequently ships smaller-than-56px tap targets not under this project's control
- Keyboard/typed entry still works as a fallback for desktop mouse+keyboard users
- Locale: the input's displayed format follows OS locale automatically; the value is always
  normalized to ISO `yyyy-mm-dd` in the DOM, and this app formats it to `dd/mm/aaaa` for display
  everywhere else (list, badges, emails) via `date-fns` with `ptBR` locale (already in the
  approved stack) — so the *storage/transport* format is unambiguous while every *displayed*
  instance is Brazilian-conventional
- Trade-off accepted: native date inputs have inconsistent visual styling across browsers. This
  is judged acceptable because functional accessibility (large, OS-native, familiar tap target)
  outweighs visual consistency for this audience — Phase 3 may add a minimal custom-styled
  wrapper later if visual inconsistency proves to be a real user complaint, but should not
  replace the underlying native `<input type="date">` element itself.

Field styling: `min-h-14`, `px-4 py-3`, `text-xl`, same border/focus treatment as every other
input, label `Prazo` above (not a floating/placeholder-only label).

## Responsável Field — Select Approach

**Decision: native `<select>`, no custom combobox/autocomplete.**

Same rationale family as the date field: native selects trigger the OS's own picker UI (a
full-screen scrollable list on mobile), are guaranteed accessible by default (labelled, keyboard-
navigable, screen-reader compatible without extra ARIA work), and avoid a JS-library dependency
in a phase that doesn't otherwise need one. The list of institution volunteers is expected to be
small (dozens, not hundreds) per the project's actual scale, so a searchable/filterable combobox
is not warranted — reconsider only if the volunteer roster grows enough to make scrolling a
native select genuinely painful, which is out of scope to speculate on now.

## Open Decisions (flagged for later review, not blocking)

1. **shadcn/ui deferral.** This phase builds plain-Tailwind native form elements instead of
   running `shadcn init`, to stay unblocked without an interactive preset-selection prompt.
   Phase 3 should evaluate whether to retrofit these components onto shadcn primitives
   (Button, Input, Select, Badge) or keep the native-element approach permanently — both are
   viable given the accessibility floor is already met natively.
2. **`área/projeto` as free text vs. a fixed/managed list.** This spec treats área/projeto as a
   free-text input (simplest for Phase 4, unblocks DEM-01 immediately). Phase 5's filtering/
   grouping requirement (DEM-04) will read much better against a constrained, coordinator-managed
   list of áreas rather than free text prone to typos/duplicates ("Pesquisa de Campo" vs
   "pesquisa campo"). Recommend Phase 5 (or a dedicated data-model refinement) revisit this as a
   proper `areas` table with a select, not a Phase 4 blocker.
3. **Skeleton loading state exact timing.** Marked as a 🧪 backstop above — the 3-card skeleton
   is specified visually but whether the initial Server Component fetch is fast enough to make it
   imperceptible in practice (likely, given Supabase free tier + small data volume) is left for
   verification rather than assumed away.
