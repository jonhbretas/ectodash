<objective>
**Phase goal (per ROADMAP.md):** Users can create, edit, and track the status of demandas (tasks), with overdue items flagged automatically without manual marking.

**This is the phase's tracer slice** — one thin, production-quality path wired through every layer: a Client Component form, a shared zod validation schema, a Server Action, the RLS-protected `demandas` + `demanda_responsaveis` tables from plan 04-01, and a Server Component read back on the dashboard. It proves DEM-01 end-to-end, including the one decision most likely to have an architectural gap if done wrong: a demanda created with multiple responsáveis actually produces multiple rows in the link table, not a UI illusion over a single-FK backend.

Per critical_constraint 6, this is the first phase shipping real screens on a project the user is watching deploy live — this plan's own scope is deliberately the smallest slice that produces a genuinely usable "create a demanda and see it" loop in production, before Wave 3 expands into edit/conclude and visual polish.

Purpose: catch any architectural mismatch between the multi-responsável schema and the form/action layer after one plan, not after edit, conclude, and list-polish are all already built on top of an assumption that turns out wrong.
Output: a signed-in user can create a demanda with multiple responsáveis through a real form and see it appear on the dashboard, in production.
</objective>

    **2. `src/app/(dashboard)/demandas/demanda-schema.ts`** — a single zod schema imported by both the form and the Server Action, per RESEARCH.md Pattern 5:
    - `titulo`: `z.string().trim().min(1, "Digite um título para a demanda.")` (exact error copy from 04-UI-SPEC.md's Copywriting Contract).
    - `responsavelIds`: `z.array(z.string().uuid()).min(1, "Escolha quem é o responsável.")` — an array, not a single string, since this is the multi-responsável field (CONTEXT.md).
    - `prazo`: `z.string().date("Escolha uma data de prazo.")` (native `<input type="date">` yields `yyyy-mm-dd`).
    - `status`: `z.enum(["pendente", "em_andamento", "concluida"])`.
    - `area`: `z.string().trim().optional()`.
    Export the inferred type as `DemandaFormValues`.

    **3. `src/app/(dashboard)/demandas/demanda-form.tsx`** — a Client Component (`"use client"`), following 04-UI-SPEC.md's Screen Inventory section 3 exactly for field order, labels, copy, and styling (`min-h-14`, `text-xl`, `px-4 py-3`, `max-w-md`, `gap-4`, the `Campos com * são obrigatórios.` legend, placeholder examples). Use `react-hook-form`'s `useForm` with `zodResolver(demandaSchema)`. Fields:

    - Responsável — a native multi-select: `<select multiple>` sized to show several options at once (not a single-line dropdown), populated from a `profiles` list passed in as a prop (fetched server-side by the page, per 04-UI-SPEC.md's "Responsável Field — Select Approach": native controls only, no combobox library). Label `Responsável` with the required-field asterisk.
    - Prazo — native `<input type="date">`, per 04-UI-SPEC.md's "Date Input Approach".
    - Status — `<select>` with the 3 status options, Brazilian Portuguese labels (`Pendente` / `Em andamento` / `Concluída`) mapped to the enum values, defaulting to `Pendente` on create, no empty option.
    - Área/projeto — `<input type="text">`, explicitly optional, no asterisk, placeholder `Ex: Pesquisa de Campo`.
    Submit button: `Criar demanda`, full width, `min-h-14`, `bg-blue-700`; a `SubmitButton` inner component using `useFormStatus` for the `Criando...` pending label, mirroring `login-form.tsx`'s `SubmitButton` pattern exactly.     **4. `src/app/(dashboard)/demandas/actions.ts`** — `"use server"`. Export `createDemanda(prevState, formData)`:
    - `supabase.auth.getUser()` — if no user, return `{ ok: false, message: "Sessão expirada. Faça login novamente." }`.
    - Parse `formData` with `demandaSchema.safeParse(...)`. `responsavelIds` arrives from a multi-select as multiple same-named `formData.getAll("responsavelIds")` entries — read it that way, not via `Object.fromEntries(formData)` alone (which collapses repeated keys to the last value). Build the object to parse manually: `{ titulo: formData.get("titulo"), responsavelIds: formData.getAll("responsavelIds"), prazo: formData.get("prazo"), status: formData.get("status"), area: formData.get("area") || undefined }`. If parsing fails, return `{ ok: false, message: "Verifique os campos destacados." }`.
    - Insert into `demandas`: `{ titulo, prazo, status, area }` only — do NOT include `criado_por` in the payload; the column default `(select auth.uid())` and the INSERT policy's `WITH CHECK` both derive it server-side from the session (RESEARCH.md Pitfall 4, proven live in plan 04-01). Use `.select("id").single()` to get the new row's id back.
    - If the demanda insert fails, log via `console.error` and return `{ ok: false, message: "Não foi possível salvar a demanda agora. Verifique sua internet e tente de novo." }` (exact copy from 04-UI-SPEC.md).
    - Insert into `demanda_responsaveis`: one row per id in `parsed.data.responsavelIds`, `{ demanda_id: newDemandaId, profile_id }`. Use a single batched `.insert([...])` call, not a loop of individual inserts.
    - If the responsáveis insert fails, log the error but still `revalidatePath("/")` and return a success-shaped message — do not leave the user on a broken screen for a partial failure on a demanda that was already created; note this tradeoff in the SUMMARY as a known gap (no transaction spans both inserts in this plan — Supabase JS does not expose multi-table transactions without an RPC function, and building one is out of scope for the tracer).
    - `revalidatePath("/")`. Return `{ ok: true, message: "Demanda criada com sucesso." }`.

Fetch the list of profiles for the responsável select (`supabase.from("profiles").select("id, email").order("email")` — use `email` as the display label since no `full_name` column exists on `profiles` per `0001_profiles.sql`; note this as a known limitation, not a blocker). <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client-submitted form data -> createDemanda Server Action | Untrusted input crosses here; zod re-validates server-side even though the client also validates |
| createDemanda -> public.demandas / public.demanda_responsaveis INSERT | RLS from plan 04-01 is the real authorization boundary; the Server Action does not reimplement "can this user create a demanda" |
| Server Component page.tsx -> demandas_com_status SELECT | Every authenticated user reads every demanda this phase (Phase 5 narrows later) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-07 | Tampering | Client submitting a fabricated `criado_por` in `formData` | high | mitigate | The Server Action never reads a `criado_por` key from `formData` at all; the column default and plan 04-01's INSERT policy `WITH CHECK` both derive it from `auth.uid()` server-side |
| T-04-08 | Tampering | Client submitting a `responsavelIds` array containing an arbitrary/non-existent profile id | low | accept | The `demanda_responsaveis.profile_id` foreign key to `public.profiles` rejects any id that isn't a real profile at the database level; the insert fails cleanly and surfaces the generic save-failure message, no invalid link is ever persisted |
| T-04-09 | Denial of Service | Unbounded profiles list rendered into a single native `<select multiple>` if the institution's volunteer roster grows large | low | accept | 04-UI-SPEC.md's own "Responsável Field" section explicitly judges this acceptable at the project's actual scale (dozens, not hundreds) and defers a searchable control to a future phase if the roster ever grows enough to matter |
| T-04-10 | Repudiation | Partial-failure path where a demanda is created but its responsáveis insert fails, leaving an orphaned demanda with zero responsáveis and a success-shaped user message | medium | accept | Explicitly documented as a known tradeoff in this plan's action steps and to be recorded in the SUMMARY; Supabase JS has no multi-table client transaction primitive without a custom RPC, which is out of scope for the tracer slice — revisit if this proves to be a real occurrence in practice |
| T-04-SC | Tampering | npm/pip/cargo installs | low | accept | `react-hook-form`, `@hookform/resolvers`, `date-fns`, `lucide-react` — all `[OK]`/resolved-false-positive in 04-RESEARCH.md's Package Legitimacy Audit; no new checkpoint required |
</threat_model>
