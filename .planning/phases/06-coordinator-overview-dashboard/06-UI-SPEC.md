# Phase 6 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Sequencing Note (read first)

No `06-RESEARCH.md` existed at the time this contract was written (checked — directory did not
exist before this file created it). This document proceeds on direct inspection of the shipped
Phase 4/5 code (`src/app/(dashboard)/page.tsx`, `demanda-list.tsx`, `demanda-filters.tsx`,
`status-badge.tsx`, `overdue-badge.tsx`) plus the locked token language in `03-UI-SPEC.md` and
`05-UI-SPEC.md`. If `06-RESEARCH.md` lands with a conflicting technical recommendation (e.g. a
different aggregate-query strategy), the planner reconciles the **query mechanics** against that
document, but the **visual contract** below — layout, copy, color reuse — holds regardless, per
this project's established precedent for handling out-of-order artifacts (03-UI-SPEC.md, 05-UI-SPEC.md).

**This is a genuinely new UI surface, not a retrofit.** Phase 5's `/` route is a per-row, filtered
*list* (each row is one demanda). This phase adds an aggregate *analytics summary* — counts,
groupings, an overdue highlight — that answers "how is the institution doing," not "show me every
row." No new hue, spacing value, type size, icon language, or shadcn component is introduced; this
phase is disciplined reuse of the Phase 3/5 token language applied to a new information shape
(counts and groups instead of rows).

**No chart library is introduced this phase.** Large accessible stat-cards/count tiles satisfy
COORD-01/02/03 at this data scale (a nonprofit's total demanda volume is expected to be dozens-to-
low-hundreds, not thousands) — a chart adds a dependency, a legend/tooltip a11y surface, and visual
complexity this elderly-inclusive audience does not need to read three numbers. CLAUDE.md's stack
recommendation reserves Recharts/Tremor for Phase 10's financial dashboard (entradas/saídas/
resultado over time — a genuinely temporal, chart-shaped need); Phase 6's need (status counts,
grouped counts) is table/tile-shaped, not trend-shaped. If a future phase's RESEARCH.md finds real
user need for a trend view here, that is an additive change, not a contradiction of this contract.

| Token | Value | Usage |
|-------|-------|-------|

read-only displays, so no touch-target minimum applies to the card body itself, only to any
button/link it contains.

## Typography

Unchanged 3-size/2-weight scale — no new size introduced. One addition: a large numeral treatment
for stat-card counts, built from the existing `text-3xl`/30px display size (not a new size).

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body / meta text (breakdown row labels, card sub-labels) | 20px (`text-xl`) | 400 regular | 1.5 |
| Small / hint (breakdown row counts when inline, "atualizado agora" style meta) | 16px (`text-base`) | 400 regular / 600 semibold for counts | 1.5 |
| Heading (page title `Painel do coordenador`, section headings) | 24px (`text-2xl`) | 600 semibold | 1.2 |
| Display (stat-card big number, empty-institution state heading) | 30px (`text-3xl`) | 600 semibold | 1.2 |

**Stat-card number treatment:** the large count uses `text-3xl font-semibold` (identical to the
existing display size — no new "hero number" size is introduced, resisting the temptation to make
dashboard numbers even bigger than the locked scale allows). The card's label sits above the
number at `text-xl font-medium text-zinc-700` (body size, not shrunk to meta size — this audience's
accessibility floor applies to dashboard labels exactly as it does to form labels).

reserved for the one number that needs the coordenador's attention first. This directly answers
COORD-02 ("overdue demandas... highlighted") with the same red/`AlertTriangle` visual language
already proven at the row level, scaled up, rather than inventing a new "dashboard alert" color.

**Non-color-alone compliance:** the overdue stat card carries the word "Atrasadas" and the
`AlertTriangle` icon alongside the red fill and the numeral — a colorblind coordenador reads
"Atrasadas: 7" regardless of color perception, identical to how `overdue-badge.tsx` already reads
"Atrasada" next to its icon.

## Route & Access Contract

**Decision: new dedicated route, `/painel`, not a conditional section bolted onto `/`.**

Rationale:
- `/` is already a real, working surface (Phase 4/5's filtered demandas list) used by every role
  every day. Overloading it with a second, structurally different rendering mode (aggregate
  summary vs. per-row list) behind a role check makes `/`'s Server Component do two unrelated jobs
  and doubles its data-fetching surface for zero benefit — a coordenador who wants the row-level
  list still needs `/` to behave exactly as it does today.
- A separate route gives the coordenador a clean, bookmarkable, back-button-safe destination
  (`/painel`) distinct from their row-level list, consistent with this project's existing
  URL-driven-state philosophy (05-UI-SPEC.md's Filter State Pattern) — "where am I" is legible from
  the URL alone.
- COORD-01/02/03 describe a *single dashboard* as the deliverable, which reads naturally as "one
  page whose whole purpose is this summary," not "an extra `if` branch inside the existing list
  page."

**Route:** `/painel` (Portuguese, matching every other route's language — `/demandas`,
`/login` — not `/dashboard` or `/coordenador`, since "dashboard" is already the internal/dev name
for the whole `(dashboard)` route group and would be a confusing route segment; "painel" is the
established PT-BR term used verbatim in the page heading copy above).

**Access control — UX layer only (RLS remains the actual authorization boundary, per CLAUDE.md's
explicit prohibition on client-side-only authorization):**

- The page is a Server Component that reads `profiles.role` the same way `(dashboard)/page.tsx`
  already does (identical `supabase.auth.getUser()` + `profiles` read pattern — no new auth
  mechanism).
- **If `role === "coordenador_geral"`:** render the full dashboard (stat cards + breakdowns).
- **If `role !== "coordenador_geral"` (líder de área, voluntário comum, financeiro, or any other/
  unknown role):** render the **non-coordenador state** (heading + body + CTA above) at
  `/painel` itself — **not a redirect**.

**Why a same-URL access-denied state, not a redirect:** a silent `redirect("/")` on a role mismatch
is worse UX for this project's elderly-inclusive, low-technical-confidence audience — a user who
followed a link (e.g. pasted from a coordenador, or a stray bookmark) and gets silently bounced to
a different page with no explanation may think the link is broken or they made an error, and will
likely retry the same action repeatedly. An explicit, calm "this page isn't for your role, here's
where to go instead" message is more legible and matches this project's established voice for
role-scoping (`05-UI-SPEC.md`'s scoped-view notices are the same "state the restriction plainly,
don't hide it silently" philosophy, just applied to whole-page access instead of a data subset).
This is **not a security control** — the actual data queries this page would run are still fully
governed by RLS regardless of what this UX state renders; a non-coordenador who somehow reached
this branch cannot see any data leak through it because the page's Supabase reads for the
aggregate counts only execute after the role check passes.

**No separate nav-visibility gate needed beyond this page-level check** — but as UX polish, the
link/button to `/painel` (wherever it's surfaced — see Open Decisions #2 on exact placement) is
itself only rendered for `role === "coordenador_geral"`, consistent with the existing "don't clutter
non-coordenador UI with entry points to a page they can't use" instinct already implicit in this
project (hiding is UX only; RLS + this page's own role branch are what actually matter).

## Screen Inventory

### 1. `/painel` — Coordinator dashboard (new route)

**Purpose:** answers COORD-01 (status by volunteer), COORD-02 (overdue highlighted),
COORD-03 (counts by área and by volunteer) in one page, for `coordenador_geral` only.

**Page structure, top to bottom:**

1. **Header block** — `Painel do coordenador` (`text-2xl font-semibold`, matching the existing
   `Demandas` page-title treatment) + sub-line `Visão geral de todas as demandas da instituição.`
   (`text-base text-zinc-700`) directly below, `gap-2` (8px) — same header pattern already used on
   `/`.
2. **Stat card grid** (5 cards: total, atrasadas, pendentes, em andamento, concluídas) — see layout
   below.
3. **Breakdown section — `Demandas por área`** — see §2.
4. **Breakdown section — `Demandas por voluntário`** — see §2.

**Stat card grid layout — mobile (< 640px):**
- `grid grid-cols-1 gap-4` — 5 cards stacked full-width, vertically, in this fixed order: Total,
  Atrasadas, Pendentes, Em andamento, Concluídas. Atrasadas is second (immediately after Total,
  before the neutral status breakdown), not last, so the highlighted card is seen early in the
  scroll on a small screen, not buried below three neutral cards.

**Stat card grid layout — tablet (640–1023px):**
- `grid grid-cols-2 gap-4` — Total and Atrasadas share the first row (Atrasadas still gets visual
  priority via its red fill, not via position, once the grid isn't strictly linear); remaining
  three status cards fill the next rows, 2-per-row with the last cell empty.

**Stat card grid layout — desktop (≥ 1024px):**
- `grid grid-cols-5 gap-4` — all 5 cards in a single row, same fixed order as mobile (Total,
  Atrasadas, Pendentes, Em andamento, Concluídas) so the visual scan order is identical at every
  breakpoint, only the wrapping changes.

**Each stat card (shadcn `Card`):**
- `Card` default white surface, `border border-zinc-300 rounded-lg`, internal padding via
  `CardContent` at `p-6` (24px, the existing `lg` token)
- Layout inside: icon (24px, top-left) + label (`text-xl font-medium text-zinc-700`) on one line,
  then the number (`text-3xl font-semibold`) below, `gap-2` (8px) between label row and number
- **Atrasadas card only:** `border-red-300 bg-red-100`, icon and number in `text-red-800`, icon is
  `AlertTriangle` at 24px — same hue pairing as `overdue-badge.tsx`, scaled up, never a different
  red
- Every other card: `text-zinc-900` for the number, icon colored per its matching status (amber for
  pendente, blue for em andamento, green for concluída, zinc for total) at 24px, matching exactly
  the icon colors already used in `status-badge.tsx`
- Cards are **not** links/buttons in this phase (see Open Decisions #1) — purely informational,
  `role="group"` with an `aria-label` combining the label and number for screen readers (e.g.
  `aria-label="Atrasadas: 7"`) since the visual layout (label above, number below) doesn't read as
  one sentence to assistive tech by default

### 2. Breakdown sections (`Demandas por área`, `Demandas por voluntário`)

**Purpose:** COORD-03's "counts grouped by área and by volunteer" — a simple grouped-count list,
not a chart, not a new card variant.

**Layout (identical structure for both sections, mobile and desktop — no breakpoint switch needed
since this is already a simple, narrow list, unlike the card/table switch used for demandas rows):**

- Section heading (`text-2xl font-semibold text-zinc-900`) + total-groups meta if useful (optional,
  not required copy) — e.g. no "N áreas" count is mandated, since the row count itself is visually
  obvious without a redundant header count
- Each row: `flex items-center justify-between gap-4 border-b border-zinc-200 py-4` (16px vertical
  rhythm per row, bottom-border only, no full table grid — reads more like a list than a dense data
  table, appropriate for 5–30 expected rows) —
  - Left side: the área/volunteer name (`text-xl text-zinc-900`, `truncate` per the long-text
    consideration above) + the overdue sub-count directly beneath in `text-base text-red-700` when
    `> 0` only (e.g. `2 atrasadas`) — this is the row-level echo of the same red/`AlertTriangle`
    language, just text-only at this density (no icon repetition needed 20+ times down a list;
    color+text still satisfies non-color-alone since it's paired with the word "atrasadas", never a
    bare red dot)
  - Right side: the primary count (`text-xl font-semibold text-zinc-900`, e.g. `12 demandas`)
    followed immediately by a `Ver demandas` link (`text-base text-blue-700 underline`, `min-h-14`
    tap target via padding, not visual height) that navigates to `/?area={área}` or
    `/?responsavel={id}` — reusing Phase 5's existing filter query params verbatim, no new
    filtering mechanism
- Rows sorted by primary count **descending** (busiest área/volunteer first) — this is the one
  place this phase introduces a sort rule distinct from the row-level `atrasada-first` rule, because
  the audience here ("where is the load concentrated") is different from the per-row list's
  audience ("what's most urgent right now"); ties broken alphabetically for stability
- `Sem área definida` / `Sem responsável definido` rows (when applicable) always sort **last**,
  after every named group, regardless of their count — consistent with `demanda-list.tsx`'s
  existing placement rule for the same placeholder strings

### 3. Empty-institution state (zero demandas anywhere)

Renders **instead of** the stat grid and both breakdown sections — the header block
(`Painel do coordenador` + sub-line) still renders, but everything below it is replaced by:

- Icon: lucide `ClipboardList`, 48px, `text-zinc-400` (same icon already used for the "no demandas
  at all" state on `/`, since this is the institution-wide version of the same underlying
  condition — deliberately the *same* icon, not `FilterX`, since there is no filter involved here)
- Heading (30px semibold): `Nenhuma demanda cadastrada na instituição ainda`
- Body (20px, `text-zinc-700`, `max-w-md`): `Quando as áreas começarem a cadastrar demandas, o
  resumo da instituição vai aparecer aqui.`
- CTA: `Ver demandas` button, primary blue, `min-h-14`, links to `/`

### 4. Non-coordenador access state (any role other than `coordenador_geral` at `/painel`)

Renders **instead of** the entire dashboard body, including the header block (this state gets its
own distinct heading, not `Painel do coordenador`, since a non-coordenador should never see the

sequencing would read as broken, not intentional):

- Icon: lucide `Lock` (new icon usage this phase — not yet used anywhere in the codebase; distinct
  from every other icon already in play so this state is visually unmistakable from any empty
  state), 48px, `text-zinc-400`
- Heading (30px semibold): `Este painel é exclusivo do coordenador`
- Body (20px, `text-zinc-700`, `max-w-md`): `Você não tem acesso ao painel geral da instituição.
  Toque abaixo para voltar às suas demandas.`
- CTA: `Ver minhas demandas` button, primary blue, `min-h-14`, links to `/`
- Layout: centered block, `py-16`, identical positioning to every other empty-state pattern already
  established (`demanda-list.tsx`'s two empty states) — this is the third member of that same
  visual family, not a new pattern

## Entry Point (nav link into `/painel`)

**Decision: a single text link, `Painel do coordenador`, placed on `/`'s existing header row,
visible only to `coordenador_geral`.**

Rationale: this project has no persistent nav/header component yet (`03-UI-SPEC.md`'s Open
Decisions did not mandate building one, and none has been added since) — introducing a full nav bar
is out of this phase's scope (COORD-01/02/03 describe the dashboard's content, not a navigation
redesign). The minimal, additive answer is one link, styled as a secondary/outline action
(`border-zinc-400 bg-white text-zinc-900`, matching the existing `Limpar filtros` desktop treatment)
placed next to the `Nova demanda` button in `/`'s header row (`demanda-list.tsx`'s existing
`flex ... justify-between` header), so a coordenador has one visible, obvious path in — and every
other role never sees this link at all, per the Route & Access Contract's UX-polish hiding rule.

**No new icon is needed for this link** — it is plain text, `min-h-14`, matching every other
secondary button already in the app.

## Open Decisions (flagged for later review, not blocking)

1. **Stat cards are not clickable/linked in this phase.** A coordenador who wants to see the actual
   overdue demandas behind the "Atrasadas: 7" card must currently navigate to `/` manually (there is
   no pre-built `/?atrasada=true` filter param in Phase 5's filter schema — only `area` and
   `responsavel` exist). Making the Atrasadas card link somewhere useful would require either (a) a
   new `atrasada=true` filter param added to Phase 5's `demanda-filter-schema.ts` — a schema change
   outside this UI-SPEC's scope — or (b) linking to `/` unfiltered, which doesn't meaningfully help.
   This UI-SPEC deliberately leaves all 5 top-row stat cards non-interactive and defers "click a
   stat card to filter" as a plausible future enhancement, not a requirement COORD-02 actually
   states ("highlighted" is satisfied by the visual treatment, not by a filter shortcut). The
   breakdown-row-level `Ver demandas` links (§2) already provide the one navigation affordance this
   phase's success criteria call for.
2. **Exact placement of the `Painel do coordenador` entry-point link on `/`** is specified as
   "next to `Nova demanda` in the header row" above, but the planner/executor should confirm this
   doesn't crowd that row at narrow mobile widths where both a primary and secondary button now
   stack — acceptable per the existing `flex-col sm:flex-row` pattern already used for that header,
   but worth a visual check at implementation time.
3. **Aggregate query approach** (single query with `GROUP BY`, multiple parallel queries, or
   client-side aggregation over Phase 5's existing `demandas_com_status` + `demanda_responsaveis`
   reads) is explicitly a RESEARCH.md/planner decision, not resolved here — this UI-SPEC only
   requires that the final counts be consistent with what `/`'s own filters would show for the same
   área/responsável/status, so whichever query strategy is chosen must read from the same
   role-unscoped-for-coordenador view (`demandas_com_status` has no RLS narrowing for
   `coordenador_geral` per Phase 2/5's RLS design) rather than a separate, potentially
   inconsistent aggregate table.
4. **30+ row breakdown scale** — flagged as a 🧪 backstop in UI Considerations; no pagination/
   collapse is speced, deferred to a verify-time check.
5. **Loading-state perceptibility for the aggregate queries** — flagged as a 🧪 backstop, same
   treatment prior phases gave analogous Server-Component-navigation loading questions.
