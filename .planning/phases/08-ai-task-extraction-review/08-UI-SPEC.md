## Sequencing Note (read first)

No `08-RESEARCH.md` existed at the time this contract was written (checked — the phase directory
did not exist before this file created it; a research agent may land `08-RESEARCH.md` in parallel).
This document proceeds on direct inspection of the shipped Phase 4 demanda form/schema/actions
(`demanda-form.tsx`, `demanda-schema.ts`, `nova/page.tsx`, `actions.ts`), Phase 1's pending-state
button pattern (`login-form.tsx`), and the locked token language in `03-UI-SPEC.md` / `06-UI-SPEC.md`
/ `07-RESEARCH.md`. If `08-RESEARCH.md` lands with a conflicting technical recommendation on the
**AI extraction architecture** (e.g. ephemeral client state vs. a persisted staging table, which
Gemini model/schema-enforcement approach, name-matching algorithm), the planner reconciles the
**data-flow mechanics** against that document — but the **visual contract, copy, and screen
structure** below hold regardless, per this project's established precedent for handling
out-of-order artifacts (`03-UI-SPEC.md`, `06-UI-SPEC.md` were both written before their own
RESEARCH.md landed).

**Architecture assumption this UI-SPEC makes (flagged for RESEARCH.md/planner reconciliation):**
the review screen (Screen 2) holds AI-suggested demandas as **ephemeral client-side state**, not
rows in a new persisted "draft demandas" table. Rationale: IA-04's invariant ("no demanda is ever
created without passing through human review") is most simply and verifiably satisfied when the
only place a suggestion exists before confirmation is the browser's own render state — there is no
new database row to accidentally leak into a coordenador's demandas list, no cleanup job needed for
abandoned drafts, and no new RLS surface to design for a table that only ever holds pre-confirmation
scratch data. This mirrors this project's established pattern of confirm-before-commit flows staying
client-side until the moment of commit (`demanda-form.tsx`'s own client validation before the
Server Action fires is the same shape, one level up). **If `08-RESEARCH.md` recommends a persisted
staging table instead** (e.g. to survive a page refresh mid-review, or to support a future "review
later" flow), the screens/copy below are unaffected — only the plumbing between Screen 1's AI
response and Screen 2's initial render changes (from "held in React state" to "read back from a
table"), which is invisible to the user.

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn/ui (already initialized, Phase 3) |
| Preset | `radix-vega`, base `radix`, neutral base color, Tailwind v4, `cssVariables: true` |
| Component library | Radix UI primitives via shadcn — reuses `Card` (Phase 6), `Input`, `Label`, `Select`, `Button` (Phase 3); no new shadcn component required this phase |
| Icon library | `lucide-react` (already a dependency) — `Sparkles` (AI processing/extraction, new usage this phase), `Loader2` (spin animation, processing state), `AlertCircle` (extraction error, new usage — distinct from `AlertTriangle` which is reserved for overdue/atrasada), `UserX` (responsável not matched, new usage), `CheckCircle2` (confirmed suggestion, reused from `status-badge.tsx`), `X` (reject/dismiss, new usage), `ClipboardList` (empty-extraction state, reused from `demanda-list.tsx`'s empty state) |
| Font | Geist Sans (unchanged) |

**No new shadcn component this phase.** Every primitive needed (`Card`, `Input`, `Label`, `Select`,
`Button`, `Textarea`-equivalent) already exists in `src/components/ui/` except a plain `<textarea>`,
which — consistent with this project's precedent of leaving native form elements alone when shadcn's
wrapper adds no accessibility value over a styled native element (`03-UI-SPEC.md`'s treatment of the
native `<select multiple>`) — is styled as a plain Tailwind `<textarea>`, not `npx shadcn add
textarea`. A textarea has no meaningful Radix-primitive behavior to gain (no popover, no keyboard
menu navigation) the way `Select`/`Dialog` do; only visual styling is needed, and this project's own
`Input` component's exact border/focus/padding classes are trivially reproduced on a `<textarea>`.

Unchanged from `03-UI-SPEC.md`/`06-UI-SPEC.md` — no new values introduced.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps (suggestion card status pills, fallback badge) |
| sm | 8px | Label-to-field gap within a suggestion card's editable fields |
| md | 16px | Gap between suggestion cards in the review list (`gap-4`), gap between Confirmar/Rejeitar buttons |

| 2xl | 48px | Major section breaks (paste screen to processing state transition) |

Touch targets: every interactive element (textarea submit, per-card Confirmar/Rejeitar, responsável
fallback select, "Concluir revisão" footer action) is `min-h-14` (56px), unchanged. The paste
textarea itself uses a generous `min-h-48` (192px) — not a touch-target rule, but a usability one:
a meeting summary is typically several paragraphs, and a short textarea would force excessive
scrolling for this audience before they can even see what they pasted.

## Color

Reuses the exact locked palette from `03-UI-SPEC.md`/`06-UI-SPEC.md` — no new hues, no new semantic
color introduced for this phase.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `zinc-50` bg / `zinc-900` text | Page background (via `PageContainer`, unchanged) |
| Secondary (30%) | `white` surface, `zinc-400`/`zinc-300` border | Textarea container, each suggestion `Card` |
| Accent (10%) | `blue-700` | **Reserved for:** the `Processar` submit button, the `Confirmar` button on each suggestion card, focus rings, the "Analisando..." processing-state text. **Not** used on the Rejeitar button (see Destructive below) and **not** used to pre-fill or auto-select a responsável — accent marks an action the human takes, never a value the AI silently chose |
| Destructive | `red-700` (border/text) on `red-100` (bg) | **Two uses, kept visually distinct from each other:** (1) the extraction-error state (malformed AI response / API error / empty input) — `AlertCircle` icon, exact `border-red-300 bg-red-100 text-red-800` treatment from `overdue-badge.tsx`'s hue family; (2) the "não identificado" responsável fallback badge — same hue family but paired with `UserX`, never `AlertTriangle` (that icon stays reserved for overdue demandas per `03-UI-SPEC.md`'s and `06-UI-SPEC.md`'s existing reservation, so this phase does not reuse it for a different meaning) |
| Rejeitar button | `zinc` neutral (`border-zinc-400 bg-white text-zinc-900`), **not red** | Rejecting a suggestion is a normal, expected action in a review flow (the AI is *expected* to sometimes get it wrong) — it is not a destructive action against real data, since nothing has been created yet. Coloring it red would incorrectly imply danger/an action needing extra confirmation, which contradicts IA-04's own framing that rejection is the *safe*, no-consequence path. This is a deliberate deviation from "red = reject," consistent with this project's rule that destructive-red is reserved for actions with real, hard-to-reverse consequences (per `03-UI-SPEC.md`'s reservation, which had "no delete action exists yet to spec" — this phase is the first to actually need the distinction, and resolves it as: rejecting an unconfirmed AI suggestion is not destructive) |
| Success | `green-700` | The "Criada" checkmark confirmation state on a suggestion card after `Confirmar` succeeds — exact `green-700` pairing from `status-badge.tsx`'s "Concluída" treatment, paired with `CheckCircle2` |
| Warning | `amber-700` | Not used this phase — no new warning-class state is introduced (the fallback state is destructive-red, not amber, since it *blocks* confirmation rather than merely cautioning) |
| Neutral | `zinc-100` bg / `zinc-700` text | Per-suggestion "Sugestão 1 de 4" progress meta text, disabled/already-confirmed card dimming |

**Explicit rule — the "não identificado" fallback is red, not amber, because it is a hard block, not
a caution.** A suggestion whose responsável field shows "não identificado" cannot be confirmed until
the human picks a real profile — this is functionally identical to `demanda-schema.ts`'s existing
`responsavelIds.min(1)` validation error, which already renders in `red-700` on every other demanda
form in this app (`demanda-form.tsx`'s `errors.responsavelIds` span). Reusing red (not introducing
amber-as-a-new-"needs attention" color) keeps this consistent with the existing validation-error
color, not a new severity tier.

**Non-color-alone compliance:** every colored state in this phase pairs its color with an icon and
a text label — the fallback badge reads "Responsável não identificado" next to `UserX`, the error
state reads its specific message next to `AlertCircle`, the success checkmark reads "Criada" next to
`CheckCircle2` — identical discipline to every prior phase's badges.

## Route & Access Contract

**Decision: new dedicated route, `/demandas/extrair`, not a modal or a section on `/`.**

Rationale:
- This is a genuinely new, multi-step flow (paste → processing → review → redirect), not a
  supplementary panel on an existing page — consistent with `06-UI-SPEC.md`'s reasoning for why
  `/painel` is its own route rather than a conditional branch on `/`.
- `/demandas/extrair` (not `/extrair` or `/ia`) keeps the URL grouped under the existing
  `/demandas` route segment this project already uses (`/demandas/nova`, `/demandas/{id}/editar`),
  since this feature's end product is more demandas — same URL-namespace convention, no new
  top-level route segment invented for a single feature.
- The review screen (Screen 2) is **not a second route** — it renders as a client-side state
  transition on the same `/demandas/extrair` page (paste state → processing state → review state),
  matching the "ephemeral client state" architecture assumption above. There is nothing to
  bookmark or deep-link mid-review (a suggestion list that only exists in memory), so a route change
  would only add complexity (needing to pass the extracted list through a URL or a server-persisted
  intermediate) without benefit.

**Access control — UX layer only (RLS/Server Action authorization remains the actual boundary, per
CLAUDE.md's explicit prohibition on client-side-only authorization):**

- **Role decision: `coordenador_geral` and `lider_area` only.** Per PROJECT.md's persona framing
  ("líder de área/projeto ou coordenador geral provavelmente conduz as reuniões semanais, não cada
  voluntário") and this project's existing role-scoping precedent (`page.tsx`'s `liderAreasRows`
  read, `06-UI-SPEC.md`'s coordenador-only `/painel` gate) — a `voluntario_comum` or `financeiro`
  account has no operational reason to paste a meeting summary (they don't run the weekly meeting,
  and financeiro's role is scoped to financial data per Phase 2/10, not task creation). If
  `08-RESEARCH.md` finds a different role-access recommendation, that is a reconciliation point
  per the Sequencing Note above — but absent a contradicting finding, this UI-SPEC locks the two
  roles that already have "manage this área's/institution's demandas" authority elsewhere in the
  app (créate demanda, per Phase 4/5, has no role restriction today — this feature narrows *entry
  to the AI flow specifically*, not who can create a demanda by hand).
- The page is a Server Component that reads `profiles.role` the same way `/painel` already does
  (identical `supabase.auth.getUser()` + `profiles` read pattern — no new auth mechanism).
- **If `role === "coordenador_geral"` or `role === "lider_area"`:** render the full flow (Screen 1).
- **If `role === "voluntario_comum"` or `role === "financeiro"` (or any other/unknown role):**
  render the non-authorized-role state (heading + body + CTA above) at `/demandas/extrair` itself —
  **not a redirect**, identical reasoning to `06-UI-SPEC.md`'s "explicit, calm access-denied state,
  not a silent bounce" rule for this same elderly-inclusive, low-technical-confidence audience.
- The **Server Action that actually creates each confirmed demanda** re-validates the caller's role
  server-side before inserting — this page-level UX gate is not the security boundary; the boundary
  is the same kind of server-side check `createDemanda` already implicitly relies on via RLS
  (per-role INSERT policy), extended here to also gate on role for this specific entry path if the
  planner determines a new RLS policy or a Server-Action-level role check is needed (a RESEARCH.md/
  planner decision — this UI-SPEC only requires that *some* server-side check exists, not which
  mechanism).

**No separate nav-visibility gate needed beyond this page-level check** — but as UX polish, the
link/button to `/demandas/extrair` (see Entry Point below) is itself only rendered for
`coordenador_geral` and `lider_area`, consistent with the existing "don't clutter non-eligible UI
with entry points to a page they can't use" instinct already established for `/painel`.

## Screen Inventory

### 1. `/demandas/extrair` — Screen 1: Paste (initial state)

**Purpose:** IA-01 — user pastes a ready-made meeting summary.

**Layout, top to bottom, `max-w-md` centered (matching every other form width in this app —
`demanda-form.tsx`, `login-form.tsx`):**

1. Header block — `Extrair demandas de uma reunião` (`text-2xl font-semibold`) + sub-line
   (`text-base text-zinc-700`) directly below, `gap-2`.
2. Form (`flex flex-col gap-4`, mirrors `demanda-form.tsx`'s exact structure):
   - Label `Resumo da reunião` (`text-xl font-medium text-zinc-900`) above
   - `<textarea>` — `min-h-48`, `w-full`, `rounded-lg border border-zinc-400 bg-white px-4 py-3
     text-xl text-zinc-900` + identical `focus-visible:outline` treatment to every other input in
     this app, placeholder `Cole aqui o texto do resumo da reunião...`
   - Inline validation error (`text-base text-red-700`), same span pattern as
     `demanda-form.tsx`'s `errors.titulo`
   - Submit button `Processar` — `min-h-14 w-full rounded-lg bg-blue-700 ... text-xl font-medium
     text-white`, byte-identical class list to `SubmitButton`'s idle state in both
     `demanda-form.tsx` and `login-form.tsx`
3. `aria-live="polite"` status region below the button (same pattern as every existing form),
   used for the processing sub-text and any top-level error message

**Processing state (button pending, in place — no navigation):**
- Button text switches to `Analisando...` and disables, identical mechanic to
  `demanda-form.tsx`'s `SubmitButton`'s `pending` branch (`useFormStatus`)
- A sub-text line appears directly below the button, inside the same `aria-live="polite"` region:
  `Isso pode levar alguns segundos. Não recarregue a página.` — this is the "honest about taking a
  few seconds" requirement; no spinner-only state without accompanying text, consistent with the
  non-color-alone-adjacent principle applied to loading states
- Textarea becomes read-only (not hidden) during processing so the pasted text stays visible

**Extraction-error state (renders in place of the form's success path, textarea content
preserved):**
- Icon `AlertCircle`, 32px, `text-red-700`, inline above the error text (not a full-page takeover —
  this is a recoverable, same-screen error, not a blocking page-level failure)
- Heading (`text-xl font-semibold text-red-800`): `Não foi possível analisar o resumo`
- Body (`text-base text-zinc-700`): the specific failure copy from Copywriting Contract
- CTA: `Tentar novamente` — re-submits the same textarea content (not cleared), styled as the same
  primary blue `Processar`-style button, replacing the disabled `Analisando...` button in place

### 2. `/demandas/extrair` — Screen 2: Review (client-state transition, same route)

**Purpose:** IA-03 (suggestions with título/responsável/prazo) + IA-04 (human review/edit/reject
before creation).

**Layout, top to bottom, `max-w-2xl` centered (wider than the paste screen's `max-w-md` — this
screen holds a list of multi-field cards, not a single form, so it earns the wider Phase 6-style
content width already established for list/breakdown surfaces):**

1. Header block — `Revisar demandas sugeridas` (`text-2xl font-semibold`) + sub-line with the live
   count (`text-base text-zinc-700`).
2. Suggestion card list (`flex flex-col gap-4`) — one shadcn `Card` per extracted suggestion, in
   the order the AI returned them (no re-sorting — the meeting summary's own narrative order is
   the most legible order for a human cross-checking against their memory of the meeting).
3. Sticky/fixed footer action bar (`border-t border-zinc-300 bg-white`, `p-4`, matching this
   project's existing bottom-anchored-action convention) — progress meta (`{X} de {N}
   revisadas`) + `Concluir revisão` button.

**Each suggestion card (shadcn `Card`, `p-6`):**

- Card title: `Sugestão {i} de {N}` (`text-xl font-semibold text-zinc-900`)
- Editable fields, identical label-above-field convention to `demanda-form.tsx` (not a re-invented
  layout):
  - `Título *` — `Input`, pre-filled with the AI's extracted string, fully editable,
    `min-h-14 text-xl`
  - `Responsável *` — **two possible renderings depending on match state:**
    - **Matched:** a `Select` pre-filled with the matched profile (by email, same display
      convention as `demanda-form.tsx`'s `profiles.email` labels), still changeable by the human
      (the AI's match is a suggestion, not a lock)
    - **Unmatched ("não identificado"):** the hint line `A IA identificou o nome "{nome
      extraído}", mas não encontrou esse perfil cadastrado.` (`text-base text-zinc-700`) directly
      above a `Select` whose placeholder option is `Escolha um responsável` (no option
      pre-selected) — paired with the red `UserX` + `Responsável não identificado — escolha
      manualmente` badge (`text-base text-red-800`, `bg-red-100 border-red-300`, `rounded-full
      px-2 py-0.5`, mirroring `overdue-badge.tsx`'s exact pill shape) directly beside the field
      label
  - `Prazo *` — `Input type="date"`, pre-filled with the AI's extracted date if parseable, empty
    if not (never defaulted), `min-h-14 text-xl`
  - Per-field validation errors reuse the exact `demanda-schema.ts` copy (see Copywriting
    Contract), rendered the identical way `demanda-form.tsx` already does
- Action row (`flex gap-4`, `mt-4`):
  - `Rejeitar` — secondary/neutral style (`border-zinc-400 bg-white text-zinc-900`, **not red** —
    see Color contract), `min-h-14`
  - `Confirmar` — primary blue (`bg-blue-700 text-white`), `min-h-14`, **disabled** while the
    responsável field is in its unmatched/unselected state (button is visibly present but
    non-interactive with `disabled:opacity-70`, matching the existing disabled-button treatment —
    this is the literal UI enforcement of "cannot be confirmed until a human picks a real
    profile")
- **Confirming pending state:** `Confirmar` button text switches to `Confirmando...`, both buttons
  disable, identical `useFormStatus`/pending mechanic to every other Server Action button in this
  app

**Post-confirm card state (card remains in the list, does not disappear):**
- Card body replaced with: `CheckCircle2` icon (`text-green-700`, 24px) + `Criada` (`text-xl
  font-semibold text-green-800`) + a `Ver demanda` text link (`text-base text-blue-700 underline`)
  to `/demandas/{new-id}/editar`
- Card surface dims slightly (`bg-zinc-50` instead of white) to visually recede once resolved,
  without being removed — **the card never disappears from the list**, so the human retains a
  full, scannable record of every suggestion's outcome (confirmed/rejected/pending) without needing
  to remember what already happened, which matters for an audience reviewing possibly 5-15 cards
- **Why not remove it from the list:** removing a confirmed card would shrink the list and shift
  every subsequent card upward mid-review, which is disorienting on a touch device (a tap on
  "Confirmar" that then causes the *next* card to jump into the tapped finger's position risks an
  accidental second action) — keeping every card in place, just visually resolved, avoids this

**Post-reject card state:**
- Card body replaced with: `Sugestão rejeitada` (`text-xl text-zinc-600`) + a `Desfazer` text link
  (`text-base text-blue-700 underline`) that restores the card to its editable pre-decision state
  (client-side only — rejecting never touched the server, so undo is instant and free)
- Card surface dims identically to the confirmed state (`bg-zinc-50`)

**Footer bar:**
- `{X} de {N} revisadas` (`text-base text-zinc-700`) — counts confirmed + rejected together against
  the total, updates live as each card resolves
- `Concluir revisão` button — primary blue, `min-h-14`, **disabled** until `X === N` (every
  suggestion has a resolved state); becomes enabled the moment the last pending card is confirmed
  or rejected. Pressing it navigates to `/` (see Confirmation Feedback below).
- This is a deliberate **no bulk "Confirmar todas" action** — per the phase brief's own framing,
  bulk-confirm risks making a wrong AI guess "look already saved" if a human taps it without
  reading each card, which directly undermines IA-04's intent that each suggestion gets individual
  human attention. Per-card action only; `Concluir revisão` is purely a navigation action once
  review is done, never itself a confirmation action.

### 3. Zero-suggestions state (renders in place of the card list on Screen 2, header still shows)

  `/demandas/nova`) — both secondary/outline style since neither is a clearly "more correct"

### 4. Non-authorized-role access state (any role other than `coordenador_geral`/`lider_area` at

Renders **instead of** Screen 1 entirely (identical structural precedent to `06-UI-SPEC.md`'s

## Confirmation Feedback (what happens after confirming, and where the user ends up)

**Per-suggestion confirm:** the card transitions in place to the `Criada` state (Screen Inventory
§2) — it does **not** disappear and does **not** redirect. The human stays on the review screen,
free to keep working through the remaining suggestions at their own pace. This directly answers the
"does it disappear from the list, show a checkmark, or redirect" question: **checkmark, in place,
no redirect** — the least disruptive option for a multi-item review flow, and the only one of the
three that keeps the full outcome record visible (see the "why not remove it" rationale above).

**End-of-review redirect:** pressing `Concluir revisão` (enabled only once every card is
resolved — confirmed or rejected) navigates to `/` — the existing demandas list, **not** `/painel`.
Rationale: `/` is where every created demanda actually appears regardless of who's viewing it
(coordenador and líder both land somewhere they already recognize), whereas `/painel` is
coordenador-exclusive and a líder de área running this flow would hit `06-UI-SPEC.md`'s
non-coordenador access-denied state immediately after finishing — an obviously wrong redirect
target for half of this feature's own eligible users. `/` is the one destination both eligible
roles can always land on successfully.

**Landing confirmation on `/`:** a transient `aria-live="polite"` status message —
`{X} demanda(s) criada(s) a partir do resumo da reunião.` — rendered once, above the existing
`scopedViewNotice`/filters block, using the same status-region pattern already established
throughout this app (not a toast library, not a new component — consistent with this project never
having introduced a toast/snackbar primitive in any prior phase). If `X === 0` (the user confirmed
nothing and only rejected/abandoned), no message renders — silence is correct here, not an empty
"0 demandas criadas" statement that would read as a non-event dressed up as a notification.

## Open Decisions (flagged for later review, not blocking)

1. **Three-item header row on `/` at narrow mobile widths.** Adding `Extrair demandas de reunião`
   alongside the existing `Painel do coordenador` and `Nova demanda` links means a coordenador on a
   narrow phone now sees three stacked header actions. This UI-SPEC keeps the existing
   `flex-col sm:flex-row` pattern and orders them Painel → Extrair → Nova demanda, but flags this
   for a verify-time visual check on whether three stacked `min-h-14` buttons feels crowded above
   the fold — same treatment `06-UI-SPEC.md` gave its own two-item version of this row.
2. **Loading-state timeout/cancel affordance.** Flagged as a 🧪 backstop in UI Considerations — no
   explicit cancel button or extended-wait messaging is speced for the `Analisando...` state if
   real Gemini latency runs long; deferred to a verify-time check against actual API response
   times, not assumed.
3. **15+ suggestion scroll length.** Flagged as a 🧪 backstop — no pagination/collapse speced,
   same backstop treatment `06-UI-SPEC.md` gave its analogous 30+-row breakdown question.
4. **Exact responsável name-matching algorithm** (exact string match on email/name, fuzzy match,
   or something else) is explicitly a RESEARCH.md/planner decision, not resolved here — this
   UI-SPEC only requires that the review screen have a clear, binary matched/unmatched visual state
   regardless of which matching strategy produces that boolean.
5. **Whether the AI extraction call happens via a Server Action or a Route Handler**, and which
   Gemini model/schema-enforcement mechanism is used, are explicitly RESEARCH.md/planner concerns —
   this UI-SPEC only requires that Screen 1's pending/error/success states exist and read exactly
   as specified above, regardless of the underlying call mechanism.
6. **Ephemeral-client-state vs. persisted-staging-table architecture** (see Sequencing Note) is
   flagged as the single highest-impact reconciliation point if `08-RESEARCH.md` disagrees — the
   screens above are written to be indifferent to this choice, but the planner should confirm
   before implementation which one is authoritative.
