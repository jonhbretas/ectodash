<objective>
Close Phase 2 with the checks that no command can perform.

The automated suites from plans 02-01 and 02-02 prove the role model against disposable fixture accounts. Three things remain outside their reach: whether the institution's *real* Coordenador geral account still works after a column was added to its profile row, what Supabase's own security advisors say about a newly created definer-privileged function (there is no CLI for that view), and whether the invite-with-a-role path and the written role-change procedure actually work in a human's hands rather than only in a unit test.

Purpose: RESEARCH.md names a manual confirmation that the seeded coordinator can still log in and act as coordinator as the phase gate, for a specific reason — the failure mode in Pitfall 2 is self-concealing. A coordinator demoted by the backfill cannot fix their own role, because the only policy permitting a role change requires the role they just lost. That failure would surface in Phase 6 as an inexplicable permissions bug, months after its cause.
Output: a human-confirmed record that the role model works on the institution's real account, with the advisor findings written down for later phases.
</objective>

  <what-built>
    The complete Phase 2 role model, live on the hosted project:

    - Migration `0002_profiles_role.sql` — the four fixed institutional roles as a database type, a `role` column on `public.profiles` defaulting to `voluntario_comum`, an explicit backfill restoring the Coordenador geral, the `public.has_role()` helper running with definer privileges and a pinned empty search path, its EXECUTE grant narrowed to signed-in sessions only, and a policy allowing only a Coordenador geral to change anyone's role.
    - `tests/db/role-rls.test.ts` — automated proof against the live project that a coordinator can change another volunteer's role, that a volunteer cannot change anyone's role including their own, that new accounts default to the least privilege, that the helper answers correctly for all four roles, and that the exact predicate Phase 10 will use to gate financial data admits only Financeiro and Coordenador geral.
    - `scripts/seed-coordinator.ts` with a validated role flag, and `docs/roles.md` documenting both role paths.

    This checkpoint exists because three things sit outside every one of those commands. The test suite signs in as disposable fixtures, never as the institution's real account, so it cannot detect that the account the whole institution depends on was disturbed. Supabase's security advisors have no CLI surface on this project. And a written procedure being present is not the same as it being followable.

  <how-to-verify>
    Work through all five steps and report what you actually saw at each.

    1. **The coordinator still gets in.** Open the deployed application, request a sign-in link for the Coordenador geral's institutional address, and complete the sign-in from the real inbox. EXPECTED: you land signed in, exactly as before Phase 2, seeing your address on the landing page. FAILURE SIGNAL: any error, or a page that no longer loads your profile — that would mean adding the column disturbed the read path from Phase 1.

    2. **The coordinator kept the role.** In the Supabase Dashboard, open Table Editor and select `public.profiles`. Find the row for the Coordenador geral's address and read its `role` column. EXPECTED: `coordenador_geral`. FAILURE SIGNAL: `voluntario_comum` — the backfill did not match the address, and the institution currently has no privileged account.     3. **The project's own security review.** In the Dashboard, open Advisors and select Security. Read every finding. EXPECTED: nothing new that names `has_role`, function privileges, or row-level security on `public.profiles`. Copy any finding that does mention them verbatim into your report, even if it looks harmless — this is the check that catches an over-permissive grant on a definer-privileged function, and the wording matters for whoever reads it later.

    4. **Inviting with a role, for real.** In a terminal at the repository root, invite a second address you control as a Financeiro account: `npm run seed:coordinator -- <your second address> --role=financeiro`. EXPECTED: the command exits reporting the created user id and the role `financeiro`; an invite e-mail arrives at that address; and in Table Editor the new `public.profiles` row shows `role` = `financeiro`. Then try one deliberate mistake — run the command again with a role spelled wrongly, for example `--role=financeoro`. EXPECTED: the command refuses immediately, names the four valid roles, sends no e-mail, and creates no account.

    5. **The runbook actually works.** Open `docs/roles.md` and, following only what it says, promote the account you just created from Financeiro to Líder de área. Report any step where the document left you guessing.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Automated test fixtures -> the institution's real account | Every automated check in this phase runs against disposable accounts; the real one is never exercised by any command |
| Postgres function privileges -> Supabase security advisors | The advisor view is the only surface reporting an over-permissive grant, and it exists solely in the Dashboard |
| Written procedure -> the human following it | A runbook that is present but unfollowable provides false assurance that a capability exists |
