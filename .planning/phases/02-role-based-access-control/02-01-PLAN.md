**Phase goal (verbatim from ROADMAP.md):** *The system restricts access to sensitive data based on 4 fixed institutional roles, enforced at the database level rather than only hidden in the UI.*

> Note for the reader: this Goal line is not in user-story form. Per MVP-mode rules the planner does not invent one — the phase goal is quoted as written. Run `/gsd mvp-phase 2` if a user-story framing is wanted.

This is the **tracer slice** of Phase 2: one thin path wired through every layer the phase touches — enum type, table column, backfilled data, `SECURITY DEFINER` helper function, RLS policy, hosted-project migration push, and a live integration test that exercises the whole chain as a real signed-in user.

It is production-quality, not a prototype. `public.has_role()` shipped here is the exact function Phase 4's demanda ownership, Phase 5's role-scoped visibility, Phase 6's coordinator dashboard, and Phase 10's financial dashboard will call. Nothing here is a stand-in to be replaced later.

**Decision IDs used across this phase** (02-CONTEXT.md `<decisions>` has named subsections rather than numbered IDs; this plan set maps them as follows and cites them throughout):
- **D-01** — Role Storage Model: a `role` enum column directly on `public.profiles`; 4 fixed values; one role per person; no join table.
- **D-02** — Role Assignment: role supplied as a parameter at invite/seed time, defaulting to `voluntario_comum`; changing an existing role is a documented direct database update, not a built feature.
- **D-03** — Enforcement Scope: a reusable `public.has_role()` `SECURITY DEFINER` helper plus an RLS policy using it, gating who may write `profiles.role`, proven end-to-end against the live hosted project; no financial table this phase.

Purpose: the entire engineering surface of this phase is getting one function's contract exactly right (RESEARCH.md "Key insight"). Proving it end-to-end now — including the deny direction — means a recursion failure or a silently-demoted coordinator surfaces after one commit instead of after four plans and three dependent phases.
Output: a live, versioned role model whose enforcement is demonstrated by an automated test against the real hosted project.
</objective>

    **1. `supabase/migrations/0002_profiles_role.sql`** — reproduce RESEARCH.md lines 310-347 statement for statement, in this order. Each element is load-bearing:

    - An enum type `public.app_role` with exactly these four values in this order: `coordenador_geral`, `lider_area`, `voluntario_comum`, `financeiro`. Four fixed values, no more (D-01, AUTH-02). The type — not an application-side list — is the single source of truth for what a valid role is.
    - `alter table public.profiles add column role public.app_role not null default 'voluntario_comum'`. The default is a constant, so Postgres 17.6 (confirmed from `supabase/.temp/postgres-version`) satisfies this as a catalog-only change with no full-table rewrite.
    - An `update public.profiles set role = 'coordenador_geral'` scoped by `where email = 'jonathanbretas@gmail.com'` — the institutional address seeded in Phase 1 (STATE.md, 01-03-SUMMARY.md). This statement is not optional bookkeeping: the column default just assigned `voluntario_comum` to every pre-existing row including the only privileged account in the system, and the new policy below requires `coordenador_geral` to fix that — so omitting this line locks the institution out of its own role model (RESEARCH.md Pitfall 2). The statement is naturally a no-op on any project where that address is absent, so the migration stays replayable on a fresh restore.
    - A function `public.has_role(required_role public.app_role) returns boolean`, `language sql`, `stable`, declared `security definer` with `set search_path = ''`. Its body returns whether a row exists in `public.profiles` whose `id` equals `(select auth.uid())` and whose `role` equals `required_role`. Every reference inside the body is schema-qualified because the search path is empty (RESEARCH.md Pattern 2). Declaring it `security definer` is what lets its internal lookup bypass row-level security, which is the only reason a policy defined on `public.profiles` can call it without re-entering policy evaluation on that same table forever (RESEARCH.md Pitfall 1). The sole parameter is the role being asked about — the identity is always the caller's own, never supplied by the caller.
    - `revoke execute on function public.has_role(public.app_role) from public, anon;` followed by `grant execute on function public.has_role(public.app_role) to authenticated;`. Postgres grants EXECUTE on every new function to PUBLIC automatically, which quietly makes a definer-privileged function in the `public` schema reachable by unauthenticated clients (RESEARCH.md Pitfall 3).
    - A policy named `"coordenador geral can update any profile"` on `public.profiles` `for update to authenticated`, with both `using` and `with check` set to `(select public.has_role('coordenador_geral'))`. Wrapping the call in a scalar subquery is the documented Supabase form and lets the planner evaluate it once rather than per row (RESEARCH.md Pattern 3). Deliberately add no other policy: with no UPDATE policy matching an ordinary volunteer, row-level security denies by default, which is what closes self-escalation without a single extra line.

    This migration introduces no new tables and no join table — the role lives on the existing profiles row (D-01), and the financial table is Phase 10's (CONTEXT.md Deferred Ideas).

    **Critical observation contract — read before writing assertions.** Phase 1's SELECT policy on `public.profiles` is self-only (`auth.uid() = id`), and this plan deliberately does not widen it. Consequently a coordinator updating *another* user's row gets back an empty representation: the write is permitted, but the coordinator cannot read the updated row back. Row-level security also returns success-with-zero-rows, not an error, when a policy filters an update away. **The allow case and the deny case are therefore indistinguishable from the acting client's point of view.** Never assert on the update call's returned rows or on its error field as the proof of either outcome — the only sound assertion is a re-read of the target row with the service-role admin client. An assertion written against the client response would pass identically against a completely broken policy.

    Implement these three cases:
    - Test 1 (the tracer path): a `coordenador_geral` fixture, signed in, updates a `voluntario_comum` fixture's row setting role to `lider_area`. Then re-read that row with the admin client and assert the role is now `lider_area`.
    - Test 2: a `voluntario_comum` fixture, signed in, issues the identical update against another user's row setting role to `coordenador_geral`. Re-read with the admin client and assert the target's role is unchanged.
    - Test 3: the same `voluntario_comum` fixture attempts to set the role on its OWN row to `coordenador_geral`. Re-read with the admin client and assert its role is still `voluntario_comum`. This is the headline threat — a volunteer promoting themselves — and it is closed by the absence of a self-update policy, not by anything in the application.

    In tests 2 and 3, additionally assert that any error message returned does not mention infinite recursion. A recursion failure is the specific way a caller-privileged helper fails here, and it would otherwise masquerade as a successful denial (RESEARCH.md Pitfall 1).

    If the first live assertion fails because the `role` column or the function is not visible to the Data API, that is PostgREST's schema cache lagging the migration (RESEARCH.md Pitfall 5): wait a few seconds and retry, and if it persists issue a schema-reload notification from the Dashboard SQL editor. Sending a cache-reload signal is not a schema change, so it does not breach the migrations-only rule that governs DDL.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Signed-in (`authenticated`) client -> `public.profiles.role` | Any volunteer can issue arbitrary writes against the auto-generated Data API; RLS is the only gate standing between them and their own promotion |
| RLS policy expression -> `public.has_role()` -> `public.profiles` | A definer-privileged function is invoked from a policy on the very table it reads; this loop is the phase's structural risk |
| `anon` (unauthenticated) client -> `public.has_role()` | Postgres exposes every new public-schema function to PUBLIC by default, and Supabase publishes it as an RPC endpoint |
| Developer machine -> hosted Postgres | `db push` applies arbitrary DDL with owner privileges to the live institutional database |
