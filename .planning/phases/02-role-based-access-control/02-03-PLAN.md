<objective>
Make role assignment usable. Plan 02-01 shipped the role model and proved its enforcement; without this plan the only way to give a volunteer anything other than the default is a hand-written SQL statement.

Per D-02 the assignment path is the trusted admin script, not a screen: `scripts/seed-coordinator.ts` gains a role argument, defaults to `voluntario_comum`, and validates against the four fixed values before touching the network. Per the same decision, changing an *existing* volunteer's role is documented rather than built — so this plan also writes the runbook a coordinator follows until a future phase adds an admin surface.

Purpose: an enforcement model nobody can assign roles through is an enforcement model that gets bypassed with ad-hoc SQL. A one-command invite with a validated role keeps the trusted path the convenient path.
Output: a role-aware invite command, unit-tested argument handling, and a written procedure for role changes.
</objective>

  <action>
    Split the argument handling out so it can be tested without executing the script, which performs real invites against the live project the moment it runs.

    **`scripts/lib/role-arg.ts`** — a pure module with no side effects and no Supabase import, so importing it is free. Export the four fixed role values as a `zod` enum schema built from a single const array, and export the inferred TypeScript type for that union. Export a parser that takes a raw argument array and returns either a parsed result carrying the address and the role, or a failure carrying a human-readable Brazilian Portuguese message. Treat a token beginning with the role flag prefix as the role and the first remaining token as the address, so the two can be given in either order. When no role token is present, fall back to `voluntario_comum`. Validate the role with the `zod` schema and, on failure, produce a message that lists all four accepted values — a volunteer coordinator running this at the terminal needs to see what to type, not a schema dump. Use `zod`, already a project dependency; install nothing.

    Choose the named-flag form for the role rather than a bare second positional. CONTEXT.md leaves the shape to discretion, and a named flag is self-describing in shell history and cannot be silently transposed with the address — which matters when the wrong transposition would quietly create a Coordenador geral.

    **`scripts/seed-coordinator.ts`** — keep everything already working: the environment-variable guard, the invite call, the Brazilian Portuguese error copy, and the constraint that this file lives outside `src/` and is never imported by application code because it carries the service-role key. Change three things. Parse arguments through the new module and exit non-zero with the returned message when parsing fails, before constructing any client. Update the usage line so it shows the role flag and states the default. After a successful invite, when the requested role differs from the column default, update the new user's `public.profiles` row to that role using the service-role client, keyed on the returned user id; report a failed update with a clear message and a non-zero exit rather than reporting overall success. Print the resulting role alongside the user id on success so the operator sees what was actually assigned.

    The role is applied as a second step rather than at insert time because Phase 1's trigger — not application code — creates the profiles row, and it writes only id and email. The service-role client bypasses row-level security here by design: this script is the trusted administrative path, and it is the only thing in the system that is.

    Note for whoever reads this later: the file and npm script keep their Phase 1 names even though the command now invites volunteers of any role. Renaming is deliberate churn avoided — `docs/roles.md` from Task 2 explains the command's real scope, and the name is worth revisiting when a future phase replaces the script with an admin surface.

    **`tests/scripts/role-arg.test.ts`** — cover the five cases in `<behavior>` against the parser module only. Import nothing from the seed script itself, so no test can ever trigger a real invite. These are pure unit tests with no network access and no credentials, so they run everywhere, unlike the live-project suites.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Terminal operator -> `scripts/seed-coordinator.ts` | A free-text role string from a human reaches a privileged write path |
| Seed script -> hosted Postgres with the service-role key | This client bypasses every row-level policy by design; it is the system's only trusted assignment path |
| Application code under `src/` -> role decisions | Anything here would be a bypassable check rather than a boundary, and is kept empty on purpose |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-15 | Elevation of Privilege | A mistyped or transposed role argument creating a Coordenador geral by accident | high | mitigate | Named flag rather than a bare positional so the address and role cannot be swapped; `zod` enum validation before any network call; the database enum type as an independent second layer; unit tests cover the default, each valid role, and rejection |
| T-02-16 | Elevation of Privilege | The service-role key becoming reachable over HTTP through the script or its new parser module | high | mitigate | Both files live outside `src/` and are never imported by application code; greps assert neither the script nor the elevated key name appears in the application module graph, and the build passing confirms neither joins the bundle |
| T-02-17 | Elevation of Privilege | A role check written into a page or component, giving the appearance of authorization while being trivially bypassed by calling the Data API directly | high | mitigate | A grep asserts no role identifier appears anywhere under `src/`; authorization stays entirely in the policies shipped by plan 02-01 |
| T-02-18 | Tampering | An invite reported as successful when the role update silently failed, leaving the volunteer under-privileged with nobody aware | medium | mitigate | A failed role update exits non-zero with a distinct message; the assigned role is printed on success so the operator sees the actual outcome |
| T-02-19 | Tampering | A documented role-change statement run without its address filter, rewriting every profile in the institution | medium | mitigate | The runbook gives the filtered statement shape and warns explicitly about the unfiltered form |
| T-02-20 | Information Disclosure | A real volunteer's address used as the worked example in committed documentation | low | mitigate | A grep asserts no consumer-domain address appears in the runbook; examples use placeholder addresses |
| T-02-SC | Tampering | Supply chain via package installs | low | accept | Zero new packages — the parser uses `zod`, already installed and audited `[OK]` in Phase 1 (RESEARCH.md "Package Legitimacy Audit"). No legitimacy checkpoint required |
</threat_model>
