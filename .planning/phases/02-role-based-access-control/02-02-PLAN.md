<objective>
Expand the tracer slice from plan 02-01 into full coverage of the role contract: that new accounts land on the least-privileged role, that the migration's backfill really did rescue the Coordenador geral on the live project, that `public.has_role()` answers correctly for each of the four roles, and that the precise predicate Phase 10 will use to gate financial data already evaluates correctly today.

Purpose: plan 02-01 proved the coordinator-only write path works in both directions. That is one policy. What every later phase actually depends on is the helper function returning the right answer for the right caller — Phase 4 joins demandas to it, Phase 5 scopes visibility with it, Phase 6 builds the coordinator dashboard on it, Phase 10 gates the institution's financial data on it. This plan is where that contract stops being an assumption.

ROADMAP Success Criterion 2 says a user without Financeiro or Coordenador cannot retrieve financial data even via direct API or database query. No financial table exists yet, and per D-03 none is created here. The criterion is therefore satisfied the way RESEARCH.md prescribes: by proving the reusable predicate itself, so Phase 10 applies a validated contract to a real table rather than inventing enforcement from scratch.
Output: an automated suite that fully characterises the role model against the live hosted project.
</objective>

    Prove the helper function's contract directly, since it — not any individual policy — is what Phases 4, 5, 6 and 10 consume.

    - **Per-role correctness.** Create one fixture account for each of the four roles. For each, sign in as that account and call the helper over RPC four times, once per role name, asserting it returns true for the role the session actually holds and false for the other three. Sixteen answers in total. Drive this from an array of the four role names rather than writing four near-identical blocks, so adding a fifth role later extends the matrix by editing one list. Call it through the signed-in client, never the service-role client — the service-role client bypasses row-level security and carries no `auth.uid()`, so it would exercise nothing.

    - **The Phase 10 financial predicate.** For each of the same four fixtures, evaluate the composite condition Phase 10's policy will use: holds `financeiro` OR holds `coordenador_geral`. Assert it is true for the `financeiro` and `coordenador_geral` fixtures and false for the `lider_area` and `voluntario_comum` fixtures. Add a comment above this block recording that it stands in for ROADMAP Success Criterion 2 until the real table lands in Phase 10, and that the table is deliberately absent here per D-03. Create no table, view, or column to support this — the predicate is the contract, and proving the predicate is what makes Phase 10 a one-line policy instead of a fresh security design.

    - **Unauthenticated lockdown.** Build a client from the anon key with no session and call the helper over RPC. Assert the call does not yield a boolean true — EXECUTE was revoked from unauthenticated callers in the migration, so the request is rejected. Assert on the absence of a usable answer rather than on a specific status code or message string; the exact rejection shape is a PostgREST implementation detail and pinning it would make this a brittle gate that fails on a platform update rather than on a real regression.

    - **Recursion regression guard.** Sign in as the `voluntario_comum` fixture and select its own row from `public.profiles`, including the role column. Assert the query returns exactly that one row with no error. Phase 1's self-only read policy still governs this, and the assertion exists so that if a future phase widens profile access using the helper, a policy that reads the table it guards fails loudly here rather than in production.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Signed-in client -> `public.has_role()` RPC | The helper is published as a Data API endpoint; this is the surface every later phase's authorization decision runs through |
| `anon` client -> `public.has_role()` RPC | An unauthenticated caller reaching a definer-privileged function |
| Test suite -> live institutional database | This suite creates and deletes real accounts in the production Supabase project; there is no separate test project on the free tier |
