# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Sequencing Note (read first)

Per the roadmap's Phase 3 sequencing note, this phase was deliberately deferred to run **after**
Phase 4, so it is not a greenfield foundation — it is a **formalization + polish pass** over
already-shipped screens (Phase 1 login, Phase 4 dashboard/demandas CRUD). Phase 4's own
`04-UI-SPEC.md` already established a real design language (zinc/blue/red/green/amber palette,
`text-xl`/20px body floor, `min-h-14`/56px touch targets, pt-BR copy, lucide-react icons) as
plain Tailwind v4 utility classes with **no shadcn/ui and no `components.json`**. That language
is good and already meets most of this phase's own success criteria in practice.

**This phase's job is therefore narrower than "build an accessible UI foundation from scratch":**
1. **Formalize** the ad hoc Phase 1/4 tokens into reusable CSS variables / a documented scale, so
   future phases (5–10) stop hand-copying utility-class strings from memory.
2. **Close specific accessibility gaps** Phase 4 left as open decisions or backstops (see Retrofit
   Contract below) rather than re-deriving a new visual system.
3. **Decide, finally**, the shadcn/ui question Phase 4 explicitly deferred (`04-UI-SPEC.md`'s
   Open Decision #1).
4. **Do not silently change** any visible string or Tailwind class that Phase 4 tests or the
   Phase 4 UAT depend on — verified below in Test Dependency Audit.

No `03-RESEARCH.md` existed at the time this contract was written (parallel research agent had
not yet landed a file) — this document proceeds on CLAUDE.md's explicit stack recommendation
(shadcn/ui + Tailwind v4, 18px+ base body, AA/AAA contrast, generous touch targets) plus direct
inspection of the shipped Phase 1/4 code. If `03-RESEARCH.md` lands with conflicting technical
findings, the planner should reconcile against this file rather than silently prefer one.

## Test Dependency Audit (read before touching any existing file)

Searched `tests/**/*.test.ts` for any coupling to demanda/UI copy or Tailwind classes.

**Finding: zero UI-string or CSS-class dependencies exist in the test suite.** All seven test
files (`smoke`, `db/profiles-trigger`, `auth/signInWithOtp`, `auth/session-persistence`,
`scripts/role-arg`, `db/role-rls`, `db/demandas-rls`) are either smoke tests or **live-Supabase
integration tests** that assert against database rows/RLS policies (e.g. `demandas`,
`demanda_responsaveis` table/column names) — none render or snapshot a component, and none grep
for a pt-BR string like `"Nova demanda"` or a class like `min-h-14`. There is **no automated UAT
harness** parsing rendered output in this repo as of this phase.

**Practical implication:** nothing in this phase is blocked by literal test strings. The real
constraint is **visual/behavioral continuity for the human Phase 4 UAT that already passed** —
change the pixels as little as possible for a screen a coordinator has already manually verified,
and prefer additive/internal refactors (extracting a shared `<Button>` that renders the identical
class list) over changes that alter what's on screen. The Retrofit Contract below encodes this as
the working rule: **componentize losslessly, restyle minimally.**

## Spacing Scale

Declared values (must be multiples of 4). **Identical to Phase 4's table** — this phase changes
nothing here, only promotes it from a spec-only table into real CSS variables in `globals.css`.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps (badge icon + label) |
| sm | 8px | Compact stacks: label-to-hint text, badge internal gap |
| md | 16px | Default form field gap (`gap-4`), card internal padding |
| lg | 24px | Section padding, gap between demanda cards on mobile |
| xl | 32px | Page-level vertical rhythm (header to list) |
| 2xl | 48px | Major section breaks (list to empty-state illustration block) |
| 3xl | 64px | Page padding on desktop (`py-16`, matches login page) |

Exceptions: none. Touch targets remain `min-h-14` (56px) minimum across every interactive
element — buttons, inputs, selects, the entire tappable card surface — unchanged from Phase 4.

**New in this phase:** these values are promoted from "a table in a markdown file" to actual
`@theme` CSS variables in `globals.css` (`--spacing-xs` through `--spacing-3xl`), so `gap-[var(--spacing-md)]`-style
usage becomes possible and future phases stop re-typing `gap-4`/`p-4` from memory. Existing
utility classes (`gap-4`, `p-4`, `py-16`, etc.) are **not required to be rewritten** to the
variable form — Tailwind's default spacing scale already maps 1:1 to these values (`4 = 16px`,
etc.), so this is a documentation/token-naming exercise, not a rewrite.

## Typography

3 sizes, 2 weights — **identical scale to Phase 4's table**, now formalized as the canonical
project-wide scale (Phase 4's table explicitly said Phase 3 should "lift this table directly").

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body / input / label | 20px (`text-xl`) | 400 regular | 1.5 |
| Small / hint / meta (badge text, counts) | 16px (`text-base`) | 400 regular / 600 semibold for badge labels | 1.5 |
| Heading (page title, card título) | 24px (`text-2xl`) | 600 semibold | 1.2 |
| Display (empty-state heading only) | 30px (`text-3xl`) | 600 semibold | 1.2 |

No text anywhere in the app is smaller than 16px. No new sizes introduced. This phase's only
typography change is formalizing these four rows as `@theme` tokens (`--text-body`,
`--text-meta`, `--text-heading`, `--text-display` mapped to the existing Tailwind scale) so a
future PR reviewer can point at "the type scale" instead of "whatever `04-UI-SPEC.md` said."

## Color

**Formalizes Phase 4's exact zinc/blue/red/green/amber palette as CSS variables** — no new hues,
no changed hex values. All pairs already meet WCAG AA (4.5:1) as verified in Phase 4's spec.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `zinc-50` (#FAFAFA) bg / `zinc-900` (#171717) text | Page background, primary body text — contrast 19.6:1 |
| Secondary (30%) | `white` (#FFFFFF) surface, `zinc-400`/`zinc-300` border | Demanda cards, form containers, input borders, table surface |
| Accent (10%) | `blue-700` (#1D4ED8) | **Reserved for:** primary CTA buttons ("Nova demanda", "Criar demanda", "Salvar alterações", "Enviar link de acesso"), active/focused input outline, text links, the "em andamento" status badge |
| Destructive | `red-700` (#B91C1C) | **Reserved for:** atrasada (overdue) flag, field validation error text/border. No delete action exists yet in the shipped app (Phase 4 explicitly deferred deletion) — this role is reserved but has no destructive-confirmation UI to spec yet |
| Success/neutral-positive | `green-700` (#15803D) | **Reserved for:** "concluída" status badge, "Marcar como concluída" button only |
| Warning | `amber-700` (#B45309) | **Reserved for:** "pendente" status badge only, always paired with an icon + text label, never alone |

Accent reserved for: primary submit/create buttons, active focus ring, text links, "em andamento"
status badge fill — **unchanged from Phase 4**, restated here because this is now the canonical
source of truth other phases point to instead of `04-UI-SPEC.md`.

**New in this phase:** promote this table into real `@theme` variables in `globals.css`
(`--color-surface`, `--color-surface-secondary`, `--color-accent`, `--color-destructive`,
`--color-success`, `--color-warning`) mapped to the exact hex values above, so shadcn's
generated component variants (`<Button variant="destructive">`, etc.) resolve to these same
values rather than shadcn's stock red/green, which have not been contrast-checked for this
project. **Do not let `shadcn init` overwrite `globals.css`'s existing `--background`/
`--foreground` variables with its own light/dark defaults without first reconciling them against
this table** — this is the single highest-risk step in the shadcn adoption (see Retrofit
Contract, Step 2).

**Explicit non-color-alone rule (carried forward unchanged):** every status and the overdue flag
pairs color with both an icon and a text label. This phase does not touch that logic — it already
passes Phase 4's own dimension.

## Copywriting Contract

No new user-facing copy is introduced by this phase — it is a visual/structural retrofit, not a
new screen. Existing Phase 1/4 copy carries forward **verbatim, character-for-character**,
because there is no requirement in Phase 3's success criteria that any string change, and
changing established copy the coordinator/volunteers have already seen would be a regression, not
progress, for an elderly-inclusive audience who benefits from *consistency* above all.

| Element | Copy | Source (must stay identical) |
|---------|------|-------------------------------|
| Primary CTA (list view) | `Nova demanda` | `demanda-list.tsx` |
| Primary CTA (create form submit) | `Criar demanda` | `demanda-form.tsx` |
| Primary CTA (edit form submit) | `Salvar alterações` | `demanda-form.tsx` |
| Secondary CTA (cancel) | `Cancelar` | `demanda-form.tsx` |
| Mark-as-concluded action | `Marcar como concluída` | `conclude-button.tsx` |
| Empty state heading | `Nenhuma demanda cadastrada ainda` | `demanda-list.tsx` |
| Empty state body | `Quando alguém criar uma demanda, ela vai aparecer aqui. Toque em "Nova demanda" para começar.` | `demanda-list.tsx` |
| Status labels | `Pendente` / `Em andamento` / `Concluída` | `status-badge.tsx` |
| Overdue flag | `Atrasada` (badge), `Atrasada — prazo era {data}` (aria-label) | `overdue-badge.tsx` |
| Login CTA | `Enviar link de acesso` | `login-form.tsx` |
| Login label | `E-mail institucional` | `login-form.tsx` |
| Field labels | `Título`, `Responsável`, `Prazo`, `Status`, `Área ou projeto` | `demanda-form.tsx` |
| Required-field legend | `Campos com * são obrigatórios.` | `demanda-form.tsx` |

**Rule for this phase:** if a shadcn component wraps one of these strings (e.g. `<Button>Nova
demanda</Button>` replacing a raw `<Link>` with the same text), the visible text node **must
remain byte-identical**. No rewording, no capitalization change, no punctuation change, even if
the executor feels a shadcn-idiomatic label would read better.

**Genuinely new copy needed this phase (from accessibility gap-closing, not new screens):**

| Element | Copy |
|---------|------|
| Skip-to-content link (new — WCAG 2.4.1, benefits keyboard/screen-reader users, zero visual cost for mouse/touch users) | `Pular para o conteúdo principal` |
| Reduced-motion toggle (only if implemented — see Open Decisions) | Not speced this phase — deferred, see Open Decisions #3 |

## UI Considerations

Applicable state considerations resolved: 4 covered, 2 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| overflow | Any body text at 200% browser zoom (WCAG 1.4.4 Resize Text) | 🧪 backstop | No layout in Phase 1/4 uses fixed pixel widths that would clip at 200% zoom (all use `max-w-md`/`max-w-4xl` + fluid `flex`/`gap` layouts) — but this has never been manually verified at 200% zoom; requires a held-out manual check at verify time rather than assumed |
| long-text | Focus-visible ring on every interactive element (WCAG 2.4.7) | ✅ covered | Every button/input/link in the shipped code already carries `focus-visible:outline focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-blue-700` — this phase's formalization must preserve this exact utility chain on every element it touches, verified by grep before/after |
| populated | Reduced-motion users (`prefers-reduced-motion`) | 🧪 backstop | No animations exist beyond `transition-colors` (hover states) — likely harmless even under reduced-motion, but not yet gated behind a `@media (prefers-reduced-motion: reduce)` rule; flag for verify-time check rather than assume |
| empty | Keyboard-only navigation (no mouse) across login → dashboard → create/edit form | ✅ covered | All interactive elements are native `<button>`/`<a>`/`<input>`/`<select>` (no `<div onClick>` patterns found in any file read) — keyboard operability is structural, not a gap to close |
| overflow | Skip-link target (new) | ✅ covered | New `Pular para o conteúdo principal` link added to `layout.tsx`, targets a `id="main-content"` anchor added to each page's `<main>` element — copy specified above |
| zero-one-many | Dashboard shell — logged-in vs. logged-out layout consistency | ✅ covered | Only one authenticated shell exists (`(dashboard)/page.tsx`); no separate "no data yet" shell variant needed beyond the already-covered empty-demandas-list state |

## Retrofit Contract (the core deliverable of this phase)

This section is organized by the 4 existing surface groups named in the task brief. For each:
**what changes visually**, **what must stay pixel-identical**, and **why**.

### 1. Login (`src/app/(auth)/login/login-form.tsx`)

**Stays pixel-identical:** all copy (`E-mail institucional`, `Enviar link de acesso`,
`Enviando...`), the `min-h-14`/`text-xl`/`px-4 py-3` sizing, the `blue-700` accent, the
`aria-live="polite"` status region, `max-w-md` width.

**Changes:**
- Internally refactor the raw `<button>` into shadcn's `<Button>` component (`variant="default"
  size="lg"` mapped to identical Tailwind output via the `--color-accent` token) — **only if** the
  rendered class list and DOM text are verified identical before/after via a diff, per the Test
  Dependency Audit's "componentize losslessly" rule. If shadcn's `Button` cannot reproduce the
  exact 56px height / 20px text without fighting its own default size variants, **do not force
  it** — leave this one raw `<button>` alone rather than degrade it.
- The raw `<input type="email">` similarly becomes shadcn's `<Input>`, same identical-output
  constraint.
- Add the new skip-link (`Pular para o conteúdo principal`) once, in `layout.tsx`, benefiting
  this and every other page — not login-specific.

### 2. Dashboard shell (`src/app/(dashboard)/page.tsx`)

**Stays pixel-identical:** greeting copy (`Olá, {email}`), layout structure (`max-w-md` greeting
block above `max-w-4xl` list block), `bg-zinc-50` page background, `py-16` page padding.

**Changes:**
- This is the surface with the most legitimate accessibility gap: **no `<main>` landmark is ever
  explicitly labeled**, and there is no persistent nav/header shared across dashboard pages (the
  dashboard, create, and edit pages each independently render their own `<main>` with duplicated
  `py-16 px-6` wrapper classes). This phase should extract a single shared `<AppShell>` /
  `<PageContainer>` primitive that all three dashboard-group pages use, eliminating the
  triplicated wrapper `className` string (currently copy-pasted verbatim across
  `page.tsx`/`nova/page.tsx`/`[id]/editar/page.tsx`) — a real DRY + consistency win, not just a
  relabeling exercise.
- Add the skip-link target (`id="main-content"` on the shared `<main>`).
- No visible pixel change expected from this extraction if done correctly — the wrapper
  className string must be reproduced exactly, not redesigned.

### 3. Demanda forms (`demanda-form.tsx`, `nova/page.tsx`, `[id]/editar/page.tsx`)

**Stays pixel-identical:** every field label, every placeholder example text, the field order,
the `Campos com * são obrigatórios.` legend, the `Salvando...`/`Criando...` pending-state copy,
the `ConcludeButton`'s separate `gap-6` spacing treatment and green fill.

**Changes:**
- `<input>`/`<select>` elements become shadcn `<Input>`/`<Select>`/`<Label>` — again gated on
  identical rendered output. The `responsavelIds` multi-select (`<select multiple size={5}>`) is
  the one field shadcn's `<Select>` primitive does **not** cleanly support (shadcn's Select is
  single-value by design) — **leave this one as a raw native `<select multiple>`**, do not force
  a Combobox/multi-select library into this phase; that's explicitly Phase 5's `DEM-04`/filtering
  concern to revisit, not this phase's.
- Inline field-error `<span>` styling (`text-base text-red-700`) is preserved as-is; this already
  meets the non-color-alone-adjacent bar since it's paired with visible text, not a color-only
  border change.

### 4. Demanda list/badges (`demanda-list.tsx`, `demanda-card.tsx`, `demanda-table.tsx`,
`status-badge.tsx`, `overdue-badge.tsx`)

**Stays pixel-identical:** all status/overdue badge shapes, colors, icons, and copy exactly as
Phase 4 shipped them (this is the surface with the tightest visual language already locked and
the least benefit from changing) — count label logic (singular/plural), sort order, `line-clamp-2`
truncation, the `border-l-4 border-red-700` desktop row stripe.

**Changes:**
- `StatusBadge`/`OverdueBadge` may internally adopt shadcn's `<Badge>` primitive **only if** its
  default padding/radius can be overridden to match the existing `rounded-full px-2 py-0.5
  text-base font-semibold` exactly — same identical-output gate as above. Given `Badge`'s shadcn
  default is `rounded-md` (not full pill), this is a real risk; if reconciling class overrides
  becomes awkward, it's acceptable to leave both badge components as plain `<span>` (they already
  meet every accessibility bar Phase 3 cares about) rather than force a shadcn wrapper for its own
  sake.
- The table (`demanda-table.tsx`) keeps its native `<table>`/`<thead>`/`<tbody>` structure — shadcn's
  `Table` primitive is a thin styling wrapper over the same semantic elements, so adopting it is
  low-risk and can proceed, but the `onClick`-per-row navigation and the `border-l-4` overdue
  stripe logic must be preserved exactly.

### Cross-cutting: focus ring, spacing, contrast

No surface currently fails WCAG AA per Phase 4's own contrast computations — this phase's
"formalization" work (CSS variables) is about **naming and reuse**, not fixing contrast bugs that
don't exist yet. The one genuine, verifiable gap across all four surfaces is the **missing
skip-link** and the **un-audited 200%-zoom / reduced-motion states** flagged in UI Considerations
above — these are the actual new accessibility work in this phase, more so than any visual
restyle.

## shadcn/ui Adoption Decision

**Decision: initialize shadcn/ui now, in this phase**, resolving Phase 4's Open Decision #1.

Rationale:
- CLAUDE.md's technology stack table explicitly recommends shadcn/ui + Tailwind v4 as the
  project's standard, specifically because it "copies component source into your repo, so you can
  directly increase font sizes, touch-target padding, and contrast ratios ... without fighting a
  black-box library's theming API" — i.e., shadcn is chosen *because* it doesn't fight this
  project's already-established accessibility-first values, not despite them.
- Phase 4 deferred `shadcn init` only to avoid an interactive prompt blocking an unattended run —
  that blocker doesn't apply to this phase, which is explicitly the "formalize the design system"
  phase per the roadmap's own sequencing note.
- Five phases remain after this one (5, 6, 8, 10 all have `UI hint: yes`) that will each need
  Select/Dialog/Table/Form primitives from scratch if shadcn isn't adopted now — the cost of
  adopting later only grows.

**Migration approach: additive and conservative, not a rewrite.** Per the shadcn gate procedure —
run `npx shadcn init` with a **New York style, zinc base color, Tailwind v4** preset (closest
match to the existing palette), then add only the five components actually needed to retrofit the
four surfaces above (`button`, `input`, `label`, `select`, `badge`, `table`). Do **not** run a
blanket `shadcn add --all`, and do **not** replace every native element — per the Retrofit
Contract above, several elements (the multi-select, potentially the badges) may correctly remain
native/plain-Tailwind if shadcn's defaults can't reproduce the existing pixel output without
extra override work that isn't worth the risk this phase.

**Critical setup step:** immediately after `shadcn init`, reconcile the CLI-generated
`globals.css` `@theme` block against this document's Color/Typography/Spacing tables — shadcn
will propose its own `--background`/`--foreground`/`--primary`/`--destructive` variables with
default (non-project) hex values. These must be overridden to match the hex values locked in the
Color section above, not left as shadcn's stock palette, before any component is styled against
them.

## Open Decisions (flagged for later review, not blocking)

1. **shadcn `<Select>` vs. native multi-select for `responsavelIds`.** This phase explicitly
   keeps the native `<select multiple>` rather than forcing a shadcn/Radix multi-select, since
   shadcn's `Select` primitive is single-value by design and a proper multi-select combobox is
   Phase 5's concern (`DEM-04` filtering) if the volunteer roster grows enough to need one.
2. **Badge component migration risk.** `status-badge.tsx`/`overdue-badge.tsx` may stay plain
   `<span>` rather than adopt shadcn's `Badge` if reconciling `rounded-full` vs. shadcn's default
   `rounded-md` proves not worth the diff risk — left to the executor's judgment at implementation
   time per the "componentize losslessly, restyle minimally" rule, not mandated here.
3. **`prefers-reduced-motion` media query.** Flagged as a 🧪 backstop in UI Considerations —
   this phase does not mandate adding a reduced-motion CSS rule since no current animation is
   likely disruptive (only `transition-colors` on hover), but a verify-time check should confirm
   this judgment rather than assume it silently.
4. **200% browser zoom verification.** Also a 🧪 backstop — no layout is expected to break given
   the fluid `max-w-*`/`flex`/`gap` patterns already in use, but this has not been manually tested
   and should be checked at verify time, not assumed.
5. **`área/projeto` free-text field.** Carried over unchanged from Phase 4's Open Decision #2 —
   not this phase's concern, Phase 5 owns it.
