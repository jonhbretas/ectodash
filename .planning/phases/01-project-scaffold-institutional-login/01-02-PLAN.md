<objective>
Create the one real database read/write path of the walking skeleton: a `public.profiles` table that is populated automatically by a Postgres trigger whenever a Supabase Auth account is created, protected by Row Level Security, delivered as a versioned migration and pushed to the hosted project.

This is the identity projection every later phase joins against — Phase 2's `has_role()` RLS helper, Phase 4's demanda `responsável`, Phase 6's per-volunteer dashboard counts. Getting the trigger right here means no auth entry point can ever produce a user without a profile.

Purpose: the tracer slice in plan 01-03 cannot prove an end-to-end path without a real table on the far end. Doing the schema as a trigger (not application code) means the invite path and the magic-link path converge on the same guaranteed write.
Output: a live `public.profiles` table with RLS, a checked-in migration, and an automated integration proof.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Supabase managed `auth` schema -> application `public` schema | An elevated (`security definer`) trigger crosses this boundary on every account creation |
| Anonymous/authenticated Postgres role -> `public.profiles` | Supabase auto-generates a REST endpoint for every public table; RLS is the only gate |
| Developer machine -> hosted Postgres | `supabase db push` applies arbitrary DDL with owner privileges |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-05 | Information Disclosure | `public.profiles` exposed via auto-generated REST API | high | mitigate | `enable row level security` plus a select policy scoped to `auth.uid() = id`; proven by the anon-client negative assertion in Task 3 |
| T-01-06 | Elevation of Privilege | `public.handle_new_user()` running as `security definer` with a mutable search path | high | mitigate | `set search_path = public` pinned on the function definition; grep-enforced acceptance criterion |
| T-01-07 | Tampering | Direct row writes into Supabase's managed auth schema bypassing Auth invariants | medium | mitigate | migration only reads/attaches a trigger; negative grep asserts no INSERT/UPDATE/DELETE against the auth users table; account creation flows exclusively through the Auth Admin API |
| T-01-08 | Tampering | Schema drift between repo and hosted project via Dashboard SQL edits | medium | mitigate | all DDL delivered as versioned migration files and applied with `db push`; `migration list --linked` parity is an acceptance criterion |
| T-01-09 | Information Disclosure | Test accounts accumulating real addresses in the hosted project | low | mitigate | disposable `@example.invalid` addresses, `admin.createUser` (no outbound mail), mandatory `admin.deleteUser` cleanup |
| T-01-10 | Denial of Service | Free-tier project auto-pausing after 7 idle days, breaking login with no application error | medium | accept | Deferred to Phase 7 with a tracked follow-up — a Vercel Cron keep-alive is added when the first cron job ships (RESEARCH.md Open Question 1). Active development traffic covers the Phase 1-6 window; the Dashboard status check is an explicit `user_setup` step here |
</threat_model>
