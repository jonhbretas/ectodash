    Create the three client factories exactly per PATTERNS.md (which reproduces the official `@supabase/ssr` patterns verbatim). Concrete contract:

    - `src/lib/supabase/server.ts` — export `async function createClient()`. Calls `createServerClient` from `@supabase/ssr` with `process.env.NEXT_PUBLIC_SUPABASE_URL!` and `process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!`, passing a `cookies` object with `getAll()` returning `cookieStore.getAll()` and `setAll(cookiesToSet)` forwarding each `{ name, value, options }` to `cookieStore.set`. `cookieStore` comes from `await cookies()` (`next/headers`). Wrap the `setAll` body in a try/catch that swallows the throw: Server Components cannot write cookies, and the middleware in plan 01-03 is what actually persists the refresh — this is the documented Supabase pattern, not a bug being hidden.
    - `src/lib/supabase/client.ts` — export `function createClient()` calling `createBrowserClient` from `@supabase/ssr` with the same two `NEXT_PUBLIC_*` variables and no cookie plumbing (the browser handles cookies natively). This module must never reference the service-role variable.
    - `src/lib/supabase/middleware.ts` — export `async function updateSession(request: NextRequest): Promise<NextResponse>`. Build a `NextResponse.next({ request })`, construct `createServerClient` with a `cookies.getAll()` reading `request.cookies.getAll()` and a `cookies.setAll()` that writes to BOTH `request.cookies` and the response's cookie jar (the documented double-write is what makes the refreshed cookie visible to the same request), then `await supabase.auth.getUser()` and return the response. Use `getUser()` for validation at every server-side check point per RESEARCH.md Pitfall 3 — do not substitute the non-validating session-read alternative described there, which never exercises the refresh token and silently breaks D-03's indefinite session.
    - `.env.local.example` — committed template listing exactly these five names with placeholder values and a one-line comment each: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `NEXT_PUBLIC_SITE_URL`, `SUPABASE_PROJECT_REF`. The service-role entry carries an inline warning that it is server-only and must never be given a browser-exposed prefix.

    Do not create `.env.local` with real values in this task — that is the developer's `user_setup` step, consumed as a precondition by plans 01-02 and 01-03.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| npm registry -> developer machine | Third-party package code executes at install and build time |
| Repository -> git remote | Anything committed is permanently disclosed to everyone with repo access |
| Server runtime -> browser bundle | Any module imported by a Client Component ships its literals to the browser |
